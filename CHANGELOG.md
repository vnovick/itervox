## [Unreleased]

### Added

- **Autocomplete in the profile prompt editor** (#87). Typing `/` or `@` in the SOUL, INSTRUCTIONS or automation instruction editor lists matching skills and subagents from the skills inventory (with description and source: project, user or plugin); `{{` lists the Liquid variables profile prompts get (`issue.*`, `attempt`, `run.*`, plus `trigger.*` for automations); `|` inside `{{ … }}` lists common filters. Arrow keys, Enter and Escape work (Tab still moves focus; a caret moved away closes the list; Enter during IME composition is left to the IME), the textarea keeps its textbox role with `aria-autocomplete`, `aria-controls` and `aria-activedescendant`, and the suggestion count is announced. See [Agent Profiles](site/src/content/docs/guides/agent-profiles.mdx#autocomplete-in-the-prompt-editor).

- **Local tracker: `tracker.kind: local`** (#85). Issues are Markdown files in `.itervox/issues/` (`ITX-12.md`): front matter for title, state, priority, labels, `blocked_by` and branch, the body as the description, and comments under `## Comments`. No account, API key or labels. Edits made by hand are picked up on the next poll without a restart; the dashboard, Itervox and agent actions (create issue, comment, move state) write the files atomically, and everything survives a restart. A file that does not parse is logged and listed by `itervox doctor`, its last good version keeps being served, and Itervox does not write to it until it is fixed. `itervox init --tracker local` writes the workflow and an example issue; `itervox quickstart` chooses it when there is no `LINEAR_API_KEY` and no github.com remote (it used to stop there); `itervox demo --tracker local` runs the demo over issue files. The issues are committable: `init` adds `!.itervox/issues/` to a root `.gitignore` that hides `.itervox/`. `project_slug` is the optional identifier prefix (default `ITX`). See the [Local issues guide](site/src/content/docs/guides/local-issues.mdx).

- **`/itervox` comment commands on GitHub issues** (#84). With `tracker.comment_commands.enabled: true`, a maintainer's comment starting with `/itervox run [profile]`, `/itervox stop` or `/itervox review` dispatches the issue (resuming it or moving it to the first active state, optionally under a profile), stops its agent, or dispatches the reviewer, acknowledged with a 👍 reaction (😕 and a short reply when it cannot). Only users with write access (or in `allow`) are obeyed; bots, Itervox's own comments and the token's own account (which agents use; opt in with `allow_token_user`) never are; others are ignored, or answered with `reply_to_unauthorized`. Each comment is acted on once: its ID is recorded in `.itervox/comment_commands.json` before acting, so retries and restarts never repeat it. One repository-wide comment request per 30 seconds; permission checks are cached for 10 minutes. Documented in the GitHub guide with the security model.
- **"Claude writes, Codex reviews": the cross-review preset and read-only reviewers** (#79). `itervox init --preset cross-review` (offered `[y/N]` in a terminal when both `claude` and `codex` are installed) adds a reviewer on the other backend next to `reviewer`, with `reviewer_profiles: [reviewer-<other>, reviewer]`, `review_quorum: any_block` and `auto_review: true`, so every successful run is reviewed on both backends; `--runner codex` gives the reverse. Every reviewer is now **read-only**: the default reviewer prompt, `init`'s `reviewer_prompt` and the reviewer `SOUL.md`/`INSTRUCTIONS.md` ask for a verdict instead of a commit and push; Itervox no longer pushes the branch or commits the handoff for a reviewer run; a reviewer that moves `HEAD` (commit, pull, reset), pushes to one of the workspace's remotes (seen with `git ls-remote`, by remote name or URL, with or without a new commit, even after a reset; deleting a remote branch is not detected) or edits files outside Itervox's handoff/review/evidence directories is flagged on the issue and its verdict counts as a block; the starting point is kept across retries of the same review and retaken for each new one; a verdict from an earlier round is removed before a reviewer runs, so it is never reused. Every reviewer, a single one included, records a verdict (`approve`/`block`, `reasons`, and new line `comments`), gets the diff against the base branch plus only the latest handoff, and has its verdict posted on the issue; a closed multi-reviewer quorum posts its result too. Reviewers 2..n of a chain now get `reviewer_prompt` like the first. New guide: Cross-review preset, with the expected cost (each reviewer is a separate run).
- **`itervox doctor --upgrade`: only the upgrade notes that apply** (#82). It reads the workflow's front matter (raw, so a config that no longer loads is still explained), the environment with `.itervox/.env` loaded, the project's runtime files and the machine, and prints each v0.2.1 upgrade note or breaking change that applies with why, the concrete fix and a link to the note: worktrees or runtime state left in the v0.2.0 shared or per-slug locations (5), port 8090 already taken with no port set (6), `dependencies.auto_analyze` (9), the token no longer printed under a systemd unit (10), invalid SSH host-key checking values (11), `.WORKFLOW.md.lock` not gitignored (12), an unauthenticated daemon without `server.allowed_hosts` (13, 14), a pre-v0.2.1 PID file (15), an old systemd unit without `--shutdown-grace` / `KillMode=mixed` (17, 22), `PORT` set (19, judged as the daemon parses it), `ITERVOX_LOG_FORMAT=json` (20), token auth now required on loopback for a project that ran an older daemon there (#48), `server.allow_unauthenticated_lan`, and a backend that contradicts its command, including `agent.command`'s `claude` default and `rate_limited` `switch_to_backend` (CORE-115). With nothing to change it prints one "all clear" line and exits 0; otherwise it exits 1. Documented in the CLI reference, the deployment guide, the runbook and the compatibility notes.
- **Done needs evidence: `agent.profiles.<name>.require_evidence`** (#80). Off by default. With a list such as `[test, lint, ci]`, a successful run of that profile moves its issue to `completion_state` only with proof: each named check as a passing entry (command and output) in `.itervox/evidence/<profile>.json` (`{{ run.evidence_path }}`), stamped with the commit the checks ran on so old evidence never counts for new code (later commits may only touch `.itervox/`, such as the handoff commit, and no tracked file may have an uncommitted change), and `ci` as only-passing checks on the run's pull request (`gh pr checks`). The prompt gets an `## Evidence (required)` block. Without the evidence the issue is not moved: the run ends input-required with a "Needs evidence" reason listing what is missing, and a reply resumes the agent, whose run is checked again. Reviewer and automation runs are not gated. A non-list value (e.g. `require_evidence: true`) is a config error.
- **Agent-ready issue template** (#83). `itervox init` and `itervox quickstart` offer, after confirmation, to add `.github/ISSUE_TEMPLATE/agent-task.md` for a new GitHub workflow (`init --issue-template` / `quickstart --yes` skip the question), and never write over an existing file; `init` asks only in a terminal, so scripted runs are unchanged; on a project that already has a workflow, `init --issue-template` adds only the template. For Linear they offer to print the same sections, with blockers pointing at Linear's own relation. Sections: goal, acceptance criteria, likely files or areas, how to verify, out of scope, and blockers in the phrasing the GitHub adapter parses (`Blocked by #12, #15`; left unfilled it declares none). The template sets no labels, so a new issue is not dispatched before it is filled in. Documented in the GitHub Issues guide.
- **Opt-in "Shipped with Itervox" PR footer and README badge** (#81). `agent.pr_footer: true` (default `false`) appends a one-line `Shipped with [Itervox](https://github.com/vnovick/itervox)` footer to the body of each pull request an agent run opens on its own branch (a PR merely linked from the issue, which may be a person's, is left alone), with `gh pr edit` after a successful worker run. A hidden `<!-- itervox:shipped -->` marker keeps it to once per PR, so later runs on the same PR never duplicate it. The configuration docs include a README badge snippet.
- **`itervox demo`: try Itervox in about a minute with no keys** (#76). It writes a throwaway memory-tracker workflow in a temporary (or `--dir`) directory and runs the normal daemon with a scripted agent (`internal/agent/demoagent`) instead of `claude`/`codex`, so no agent CLI or tracker credentials are needed. The board shows ten `DEMO-n` issues moving through In Progress (with streamed activity and a fake pull request), input required (answered automatically), a failure and retry, In Review and Done within about a minute, and the dashboard header shows a **Demo mode** badge (`demoMode` in the state snapshot). Logs, workspaces and runtime files stay in the scratch directory; the dashboard opens in the browser unless `--no-open`.
- **`itervox quickstart`: one command from a repository to a running board** (#74). It detects the tracker (Linear when `LINEAR_API_KEY` is set, otherwise GitHub from a github.com `origin`) and the agent CLI (`claude`, else `codex`), writes a schema-2 `WORKFLOW.md` and agent profiles like `itervox init` (an existing schema-2 workflow is used as is; an older one is migrated only after confirmation), offers the `gh` CLI's token and saves it to `.itervox/.env` after confirmation, creates missing GitHub state labels after confirmation, runs `itervox doctor` and stops with its report on any error, then starts the daemon in its own session, waits for `/api/v1/ready` and prints the dashboard URL and the API token file. Re-running is safe: it never overwrites without asking and reports a daemon that is already running. Flags: `--yes`, `--no-start`, `--tracker`, `--runner`. The README and getting-started guide now lead with it.
- **Stacked pull requests target their blocker's branch** (#73). With `dependencies.stacked_prs: true`, a run whose worktree is stacked on its blocker's branch now gets `{{ run.pr_base_branch }}` (the blocker's branch; `workspace.base_branch` on other runs) and a `## Stacked Branch` prompt block telling the agent to open the pull request with `--base <blocker-branch>`, and after a successful worker run Itervox points the issue's open pull request (opened by the run or already linked from the issue) at that branch with `gh pr edit --base` unless it already matches. A worktree counts as stacked only when the blocker's branch is in its history and has commits `workspace.base_branch` lacks. When a dependent is restacked onto `base_branch` after its blocker lands (or already sits there), its pull request is retargeted to `base_branch` the same way, off the event loop. `gh` errors (for example a blocker branch not pushed to the remote) are logged, not fatal. An issue whose only unresolved blocker is in `tracker.completion_state` (done and in review, not merged) is now dispatched right away, stacked on that blocker's branch, so a chain of dependent issues no longer waits for each merge. The blocker's branch is the one its run used: Linear's branch name (now fetched with blocker relations), else `itervox/<identifier>`; on GitHub a blocker carrying the `completion_state` label now reads as that state instead of none. If the blocker's branch is not available locally, the fresh worktree is removed before any agent runs (a dependent branch that already has its own commits is kept) and the issue waits for the blocker as before; an existing worktree that is not stacked on the blocker is kept and the issue waits the same way, until the blocker leaves review or changes. Without `stacked_prs`, every non-terminal blocker still holds the dependent.
- **Claude Code subagents in the skills inventory, and checked skill/subagent references in profile prompts** (#86). The inventory now scans `.claude/agents/**/*.md` in the project and user home plus agents declared by plugins (name, description, tools, model, size, source), and the Settings → Skills card lists them in a **Subagents** section. Profile `SOUL.md` / `INSTRUCTIONS.md` references in explicit forms (`@agent-name`, `` `name` skill ``, `` `a`, `b`, and `c` skills ``, `` `name` subagent ``; fenced code blocks ignored, including inside lists and quotes) are resolved for the backend the profile actually runs on, computed with the dispatcher's helpers and checked against its resolver by an exhaustive test; a missing one is reported as `MISSING_SKILL_REF` / `MISSING_SUBAGENT_REF` in the dashboard's issues list and as a `WARNING:` line in `itervox doctor` (exit code unchanged). With SSH hosts configured, references that exist only outside the repository (user home or a user-installed plugin) get a `USER_SCOPE_REF_ON_SSH` note. The skills cache now also notices a new agent file (including the first one, or one added to an empty subfolder) and no longer reports itself stale because an optional file such as `CLAUDE.md` or `.claude/agents` does not exist.
- **GitHub tracker setup guide** (#77), on the site (`/guides/github-issues/`) and in `docs/github-tracker.md`: state labels with `gh label create` commands and `itervox doctor --fix`, `p0`–`p3` priority labels and how they order dispatch, blocker phrases in the issue body, `#42` identifiers and the template variables (including which ones are unset until filled and must be guarded under strict variables), `gh auth`, and a GitHub-vs-Linear comparison (no project filter, no sub-issue gating, per-issue state reads). Linked from getting-started, and `itervox doctor` prints the link with every GitHub label problem. The rewrite also corrects three errors in the previous guide: its example prompt used `{{ issue.number }}`, which does not exist and fails every dispatch under strict template variables (use `{{ issue.identifier }}`); `active_states: [open]` matches only issues labelled `open`, not all open issues; and `completion_state: closed` adds a `closed` label rather than closing the issue.
- **`itervox doctor` checks GitHub state labels; `doctor --fix` creates the missing ones** (#75). The GitHub tracker maps every state to an issue label, and a state whose label does not exist matched nothing: no issue was dispatched or moved and nothing reported why. Doctor now lists each configured state label missing on the repository (active, working, completion, terminal except `closed`, backlog and failed states, case-insensitive) with the exact `gh label create` command, and exits `1`. API failures are reported but never fail doctor; Linear workflows skip the check. `itervox doctor --fix` creates the missing labels after a `[y/N]` prompt; `--yes` / `-y` skips it for CI.

### Security

- **Go toolchain bumped to 1.26.9 and `golang.org/x/net` to v0.60.0.** `govulncheck` flagged ten standard-library advisories (GO-2026-6603/6605/6607/6608/6609/6610/6611/6612/6613/6617: HTTP/1 and HTTP/2 request handling in `net/http`, `net/textproto` and `crypto/tls`, plus their `x/net` counterparts) whose fixes ship in Go 1.26.9 and 1.27.2 only, so the 1.25 line no longer receives them. `go.mod`, the `Makefile` `GOTOOLCHAIN` pin and the container image's `GO_VERSION` move together; contributors with `GOTOOLCHAIN=auto` get the toolchain downloaded on the next build.

### Fixed

- **Itervox runs on its own repository** (#78). The repo's `WORKFLOW.md` is migrated to schema 2 (comments kept). `before_run` only fetches, and fast-forwards `main` when the workspace is still on it, so a resumed or retried run keeps its branch and unpushed work. The prompt checks out an existing issue branch (local or pushed) before creating one, and runs `make verify` instead of `go test ./...`. The `go-toolchain-sync` skill's description is quoted so strict YAML (and the skills inventory) can read it.

- **Reviewer runs are no longer stopped on an in-review issue** (found while doing #79). A reviewer is dispatched on an issue the implementer just moved to `tracker.completion_state`, usually a state that is neither active nor terminal (`in-review`), and reconciliation stopped any run on such an issue, so a review could be cut off before it finished. Reviewer runs now keep running while the issue is in `completion_state`; any other non-active state (an operator moving it to backlog) or a terminal state still stops them.
- **Saving a profile from the dashboard no longer strips `permission_mode`** (found while doing #80). The dashboard does not edit it, and the save rebuilt the profile without it, so a profile set to `sandbox` silently went back to `bypass` in `WORKFLOW.md`. It (and the new `require_evidence`) is now carried over from the saved profile.
- **Restacking now really skips a running dependent** (found while doing #73). The safety check looked the issue up by identifier in `state.Running`, which is keyed by issue ID, so it never matched: a running dependent could be rebased under its agent, with only the uncommitted-changes check in the way. It now matches by ID and by identifier.
- **The GitHub tracker no longer re-posts the branch marker comment on retries** (#72). GitHub records an issue's working branch as a hidden `<!-- itervox:branch:… -->` comment. A worker posts it whenever it does not already know the branch, and a retry whose first-turn issue-detail fetch failed starts from the list-fetched issue, which never carries one, so each such retry posted an identical comment and notified the issue's watchers again. `SetIssueBranch` now reads the latest marker first and posts only when it names a different branch; if the comments cannot be read it still posts, so the branch is never lost. Linear, which stores the branch in a field, is unchanged.
- **The GitHub tracker no longer treats pull requests as issues** (#70). GitHub's `GET /repos/{owner}/{repo}/issues` lists pull requests as well, and the tracker never filtered them, so an open pull request carrying an active-state label (`todo`, `in-progress`) became a dispatch candidate, and the `closed` fetch pulled every closed or merged pull request into the terminal-state lists. Items with a non-null `pull_request` object are now skipped in the shared paginated fetch, which covers candidates, `closed`, and label-state fetches such as the backlog.
- **`itervox init --update` no longer drops comments or reorders `WORKFLOW.md` keys** (#71). The schema-2 migration decoded the front matter into a map and re-marshalled it, which deleted every comment (including the GitHub tracker label setup notes) and sorted all keys alphabetically, with `itervox_schema_version: 2` landing in the middle of the file. The migration now edits the YAML node tree: comments, key order, quoting, block scalars, flow sequences, blank lines between sections and the file's indent width are preserved, the schema marker is inserted as the first key, and only the migrated keys change. `WORKFLOW.md.bak` behaviour is unchanged.
- **Removed a stale startup warning that claimed multi-reviewer fan-out was disabled** (#69). Fan-out has run every `agent.reviewer_profiles` entry since 0.2.1 (#58), but config loading still logged `multi-reviewer fan-out is disabled in this release; only the first agent.reviewer_profiles entry runs` whenever more than one reviewer was listed, so operators were told the opposite of what the daemon did. The warning and its stale rationale are gone; a `reviewer_profiles`-only config still promotes its first entry into `reviewer_profile` (now logged at INFO, since that configuration is valid). The 0.2.1 notes carried a contradictory "fan-out is disabled" bullet alongside the one announcing it runs; the wrong bullet is removed.

## [0.2.1] — 2026-09-28

Dependency autonomy, a write-ahead outbox for tracker writes, and the security and ops fixes that accumulated alongside them. Itervox now only picks up issues that are not blocked, orders work by what unblocks the most downstream effort, detects dependency cycles, keeps its dependency analysis fresh on its own, and captures far more real dependencies from both trackers — while making roughly 10x fewer tracker requests on the hot paths.

Tracker writes can no longer post a comment twice, and a Linear rate limit is now recognised as one instead of failing as a generic error.

### Upgrade notes

> **Read these six before upgrading — each can change which issues get worked on.**
>
> 1. **Issues that used to dispatch may now be held.** Parents with open sub-issues, and issues whose bodies match the widened blocker phrases, are now blocked. Every hold is explained in the dashboard.
> 2. **A Linear parent carrying a `blocks` relation on its own child now forms a visible 2-cycle** — both issues are held and an alert is raised. Remove the relation to resolve it.
> 3. **Blocker-unblock detection lags up to ~15 minutes** worst case (5-minute state cache plus the 10-minute refresh interval). Stale data always fails safe, i.e. still-blocked.
> 4. **The runtime project filter now narrows automations, the dashboard, and the TUI**, not just dispatch.
> 5. **Two default paths are now namespaced per project.** A project that sets
>    no `tracker.project_slug` previously shared `~/.itervox/logs` with every
>    other slugless project, and `workspace.root` defaulted to a single shared
>    `~/.itervox/workspaces` for everyone. Both now sit under a per-project
>    subdirectory. On upgrade, itervox starts from empty state in the new
>    locations: in-flight worktrees under the old shared root are not migrated,
>    so finish or discard running work before upgrading, or set
>    `workspace.root` explicitly to keep the old path. The old directories are
>    left in place and can be deleted once you are satisfied.
> 6. **`server.port` now defaults to a fixed 8090** instead of an ephemeral port. Running several daemons at once needs a distinct explicit `server.port` per repo, or `server.port: 0` to keep asking the OS for a free port.

> 7. **During a long tracker rate-limit window, tracker calls now fail immediately instead of waiting.** When Linear or GitHub publishes a reset more than 60 seconds away, calls on that tracker return a rate-limit error without sending anything until the reset, instead of blocking up to 60s and retrying into a closed window. Polling skips those ticks and logs the reset time; the outbox holds its writes until the reset. The outcome for every caller is unchanged, only faster — but expect "rate limited until HH:MM" in logs and the dashboard where you previously saw slow failures.
> 8. **`.itervox/outbox.json` entries written by this version carry a `comment_key`.** Older builds ignore it. Entries written by an older build are given a key when loaded; a comment that had already failed at least once before the upgrade keeps the old duplicate risk for that one retry.
> 9. **`dependencies.auto_analyze` is deprecated.** It still parses (`false` → `manual`, `true` → `auto`) with a startup warning; `analysis_mode` wins when both are set. If you change the mode from the dashboard, the old `auto_analyze` line stays in `WORKFLOW.md`; delete it by hand to stop the "both set" warning on every reload.
> 10. **Headless daemons no longer print the tokenised dashboard URL on stderr.** If you ran itervox under systemd, in a container, or with stderr redirected and copied the `?token=` URL out of the journal or container logs, that line is gone. Where to find the token now: if you pinned `ITERVOX_API_TOKEN` (e.g. in `.itervox/.env` — `deploy/bootstrap.sh` does this), use that value; if the daemon auto-generated one, read `<logs-dir>/api-token` (mode 0600, rewritten on every start; the startup log line `dashboard URL (token withheld from logs)` names the path and a `sha256:` fingerprint). Set `ITERVOX_PRINT_TOKEN=1` to restore the old stderr line; `--no-print-token` suppresses it everywhere, including on a terminal. The TUI's dashboard URL is unchanged.
> 11. **An invalid `agent.ssh_strict_host_checking` or `agent.ssh_strict_host_by_host` value now fails config validation.** Only `yes`, `no`, `ask`, `accept-new` and `off` are accepted (exact, lowercase). Before, a value such as `strict` or `Yes` was dropped without a word and the daemon ran with `accept-new`; now startup refuses the file (and a live reload keeps the previous config) with an error naming the field, the host for a per-host entry, and the bad value.
> 12. **WORKFLOW.md edits now create a `.WORKFLOW.md.lock` file next to it.** It is the inter-process edit lock (CORE-149): empty, safe to delete while no itervox process is running, and never worth committing. `itervox init --update` adds it to your root `.gitignore` (when one exists); otherwise add the line `.WORKFLOW.md.lock` yourself. On platforms without `flock` (Windows, not a release target) the lock is a no-op and cross-process edits are not serialized.
> 13. **With `server.allow_unauthenticated: true`, cross-origin state-changing requests are now refused.** A browser page on another origin (another port counts) that POSTs, PUTs, PATCHes or DELETEs to the API gets 403 `cross_origin_forbidden`. The dashboard itself, curl and other non-browser clients are unaffected, as is the Vite dev server on any browser from 2023 on. If you drive the API from your own web page on a different origin, give the daemon an API token (`ITERVOX_API_TOKEN`) and send it as a bearer token; token mode has no origin check (CORE-041).
> 14. **With `server.allow_unauthenticated: true`, requests addressed to an unlisted host NAME are now refused.** The daemon answers only a `Host` of `localhost`, any IP address (so LAN access by address, container probes by pod IP and SSH tunnels are unaffected), the configured `server.host`, or a name in the new `server.allowed_hosts` list; anything else gets 403 `host_not_allowed` (DNS-rebinding protection, CORE-162). `GET /api/v1/health` is exempt. **If you reach an unauthenticated daemon through a reverse-proxy, tunnel, Tailscale MagicDNS or container service hostname, add that name to `server.allowed_hosts`**, e.g. `allowed_hosts: [itervox.example.com]`. Token mode (the default) is unchanged. An entry that is a URL, has a path, or uses a wildcard now stops the config from loading; write the bare host name.
> 15. **`itervox stop` no longer signals a process the daemon lock cannot vouch for.** A PID file whose `.itervox/runtime/daemon.pid.lock` is free is removed with a "stale" message and nothing is killed. A daemon started by a pre-v0.2.1 binary (two-field PID file, no lock), or a directory-scan hit while no daemon holds the lock, is listed and `stop` exits 1; rerun with `itervox stop --legacy` after confirming the listed PIDs are itervox daemons (CORE-163).
> 16. **More daemon log lines are now `level=ERROR`, so an alert on that level fires more often — on real problems.** Three consecutive failed tracker polls (a rate limit never counts), exhausted retries, and a failed move to `tracker.failed_state` now log at Error; a worker failure that schedules a retry now logs at Warn instead of Info. A single failed poll and every rate-limited poll stay at Warn. Expect the `level=ERROR` alert from `deploy/monitoring/README.md` to fire during a tracker outage, where it stayed silent before (CORE-044).
> 17. **`SIGTERM`/`SIGINT` now drain instead of killing running turns.** The first signal stops admitting work (`/api/v1/ready` answers `503` with `"draining": true`; `resume`, `reanalyze`, `ai-review` and `provide-input` answer `409 draining`) and waits up to `--shutdown-grace` (default `30s`) for in-flight agent turns to finish; a second signal cancels them at once. Raise `--shutdown-grace` to your longest normal turn and make the service manager's stop timeout (systemd `TimeoutStopSec`, compose `stop_grace_period`) and `itervox stop --grace` exceed it, or the drain is cut short by `SIGKILL` (CORE-057).
> 18. **An operator edit to `WORKFLOW.md` now drains before it reloads.** In-flight turns finish first (bounded by `--shutdown-grace`, then cancelled); no new work starts until the edit is applied. Before, every edit cancelled every running turn (CORE-057).
> 19. **A set `PORT` environment variable now moves the dashboard port.** `ITERVOX_SERVER_HOST`, `ITERVOX_SERVER_PORT` and `PORT` override `server.host` / `server.port` (`ITERVOX_SERVER_PORT` > `PORT` > `server.port`). A shell that exports `PORT` for another project will move the bind; a set but malformed value fails startup naming the variable — only the winning one is checked, so a malformed `PORT` is ignored while `ITERVOX_SERVER_PORT` is set (CORE-058).
> 20. **Headless `--log-format json` now also makes stderr JSON.** Under systemd or in a container (no terminal), stderr log records follow `--log-format`/`ITERVOX_LOG_FORMAT` like the log file; a log shipper parsing the old text lines must switch to JSON or run with `text` (CORE-059).
> 21. **`itervox doctor` rejects unknown flags** (exit `2`) instead of ignoring them (CORE-063).
> 22. **The systemd unit changed; re-install it (re-run `bootstrap.sh`, or copy `deploy/systemd/itervox.service` and substitute `@USER@`, `@WORKDIR@` and the new `@ROOT@`), then `systemctl daemon-reload`.** `ExecStart` now passes `--shutdown-grace 240s` explicitly, `TimeoutStopSec` stays `300` (it must remain ≥ shutdown-grace + 35 s — change both together), and `KillMode=mixed` sends `SIGTERM` to the daemon only, so agent subprocesses are no longer signalled at the same instant and the CORE-057 drain can let their turns finish; a stop can therefore take up to 5 minutes. New: `RequiresMountsFor=<root>`, `RuntimeDirectory=itervox`, `EnvironmentFile=-/etc/itervox/secrets.env` and `-/run/itervox/env`, and `ExecStartPre=/usr/local/bin/fetch-secrets.sh` (installed by `bootstrap.sh`; a no-op until `ITERVOX_SECRETS_PROVIDER` is set). A hand-installed unit that lacks the script fails `ExecStartPre` — install it or drop that line. Stopping by hand: `itervox stop --grace 275s` (its default 30 s SIGKILLs a draining daemon) (CORE-057, CORE-061, CORE-062).
> 23. **`bootstrap.sh` no longer guesses a data disk.** Pass `--data-disk <stable device path>` (each `provision.sh` prints it). The earlier auto-detection of `/dev/sdb` / `/dev/nvme1n1` is gone — on Azure `/dev/sdb` is the ephemeral resource disk. New service accounts get `HOME=<root>/home` (default `/srv/itervox/home`); an existing account is moved there (state copied, `usermod -d`, old home kept) only when `--data-disk` is given, and only while the service is stopped. Log-shipping globs that point at `/home/itervox/.itervox/logs` must follow (CORE-062).
> 24. **Release archives now contain `deploy/` with its directory tree intact** (`deploy/systemd/itervox.service`, `deploy/lib/fetch-secrets.sh`, …), which `bootstrap.sh` needs to find its siblings (CORE-064).
> 25. **`PUT /api/v1/projects/filter` no longer answers `200` for a save that did not happen.** A save refused by the reload fence is `503 settings_reloading` (`Retry-After: 1`), a failed write `500 project_filter_not_saved`, and the live filter is left unchanged in both cases (before, a failed persist still changed the filter in memory). A `WORKFLOW.md` whose `tracker:` block has no `project_slug` line gets one added at the end of the block (M4-close D4).
> 26. **`POST /api/v1/deps/analyze` answers `409 draining` while the daemon drains**, and the 60 s auto-analyze scheduler skips its ticks then: an analyzer pass runs an agent, which is admission (M4-close BH-M4-3).
> 27. **A reviewer refused during a drain is remembered in `pending_reviews.json`** (next to `paused.json` in the daemon log directory; runtime state, do not commit) and dispatched after the restart; the startup workspace cleanup keeps those issues' worktrees. A downgraded daemon ignores the file (M4-close BH-M4-2).
> 28. **The published container image now includes the `claude` and `codex` CLIs** at the versions pinned in `deploy/docker/Dockerfile`; a plain local `docker build` still leaves them out (`--build-arg INSTALL_AGENT_CLIS=true` adds them). `ghcr.io/…/itervox:latest` moves only on a final release tag, not on `-rc` tags (CORE-060).
> 29. **`bootstrap.sh` now verifies the release archive against `checksums.txt`** and stops with an error on a mismatch or a missing entry, before installing anything. It also installs `itervox-upgrade.sh`, `itervox-cleanup.sh` and `itervox-watchdog.sh` into `/usr/local/bin` plus the `itervox-cleanup` and `itervox-watchdog` service/timer units — the timers are **not** enabled; enable them on purpose (`docs/deploy-runbook.md`) (CORE-107, CORE-113).
> 30. **`deploy/monitoring/heartbeat-metrics.sh` series changed.** Every series now carries an `instance` label (`--instance`, `ITERVOX_METRICS_INSTANCE`, default the host name; an AWS `Instance` dimension), GCP series are written against the `gce_instance` resource instead of `global`, and new series cover the Outbox, Cycles, Unknown, Unblocked, Attention, backend and last-crash lines. Cloud dashboards or alerts filtering the old label-less `global` series must be updated (CORE-113).
- **`auto_switched.json` has a new, versioned format.** It now also stores the per-issue `rate_limited` switch history, cooldowns and cap-comment dedupe (`{"version": 2, "overrides": …}`). A file from an older daemon is read and rewritten in the new shape on the next save. Downgrading afterwards makes the older daemon treat the envelope keys as issue identifiers: delete the file before downgrading (only pending auto-switch overrides are lost). (CORE-052)
- **A backend that contradicts the command is no longer applied.** When `agent.command` (or a profile's `command`) runs `claude` or `codex`, a different backend requested through `agent.backend`, a profile `backend`, a per-issue backend pin or a `rate_limited` `switch_to_backend` is refused, with a warning in the log and the issue log. Set a backend only for wrapper commands, or point the profile at the other backend's command. (CORE-115)
- **A backend limit now holds other issues instead of letting each rediscover it.** When a run hits a usage limit (or Claude reports three `api_retry` rate limits within 5 minutes), the backend is marked limited per worker host until the published reset (15 minutes when none is published), and other issues on it wait with the new `backend_limited` reason instead of starting and failing. Nothing is paused and no retry is consumed; queued automations stay queued. The state is kept in `backend_health.json` next to `auto_switched.json` in the daemon log directory (runtime state, do not commit). A downgraded daemon ignores the file. With a `rate_limited` rule whose switch target is itself limited, the recovery is now queued (`backend_limited`) rather than started on the limited backend.
- **`POST /api/v1/issues/{identifier}/backend` can now answer `409 backend_pin_refused`.** A pin that the dispatcher would refuse (a `codex` pin over a `claude ...` command, or the reverse) is rejected with the reason instead of being stored and silently ignored.

- **A mistyped `agent.backend_fallback` now fails config loading.** `backend_fallback: false` means off (before, it silently turned fallback ON with the default chain), `true` means on with the defaults, and any other shape — `"off"`, a number, a list, `enabled: "false"`, a non-list `chain` — is rejected with the key named. `default_cooldown_minutes` is limited to 1440.
- **Unreadable `backend_health.json` / `auto_switched.json` files are kept as `<file>.quarantine`** before the daemon starts empty and overwrites them. An `auto_switched.json` with a version other than 2 is no longer read as version 2.
- **Quarantined state files are now `<file>.quarantine.<UTC timestamp>`, at most 5 per file (CORE-173).** A second unreadable `backend_health.json`, `auto_switched.json` or automation-queue file used to overwrite the first `<file>.quarantine`; each is now kept under its own timestamped name and the oldest beyond five are removed. An existing `<file>.quarantine` from an older build is left as is.
- **`GET /api/v1/issues/{identifier}/sublog-stream` ids are now `<epoch>-<seq>` (CORE-153).** A client that stored a bare-number `Last-Event-ID` gets one `gap` frame and a full replay on its first reconnect after the upgrade. The dashboard already parses both forms.
- **`POST /api/v1/deps/analyze` can answer `409 backend_limited` (CORE-173).** While the breaker of the analyzer profile's backend is open the pass is refused (and the auto-analyze scheduler skips the tick) instead of running into the same limit.
- **`DELETE /api/v1/workspaces` answers `409 clear_in_progress` while an earlier clear is still running (CORE-114).** A second request used to start a second background clear over the same tree.
- **The container HEALTHCHECK probes the bound address family (CORE-174).** It probes `ITERVOX_SERVER_HOST` (or the host in `.itervox/dashboard_url`): an IPv6 bind (`::`, `::1`, any v6 literal) is probed on `[::1]` / that address instead of `127.0.0.1`, so a daemon bound only to `::1` is no longer reported unhealthy. The image's default `ITERVOX_SERVER_HOST=0.0.0.0` still probes `127.0.0.1`.
- **A plain `go test ./internal/agent/...` skips the slow SSH login-shell matrix (CORE-172).** Run it with `-tags sshmatrix`; `make test`, `make verify` and CI pass the tag, so nothing is dropped there.

### Added

- **Durable, async tracker writes via a write-ahead outbox.** Tracker state transitions and comments are now enqueued to `.itervox/outbox.json` and flushed by an independent worker instead of being written synchronously (with inline retries) from the orchestrator's completion/failed-state paths — a crash between "agent finished" and "tracker updated" no longer loses the transition, and a slow/rate-limited tracker call no longer blocks the event loop. Pending writes are overlaid onto the dashboard's issue state so a completed-but-unflushed issue is never re-dispatched, and are visible via a "Syncing" badge on the affected issue card, a LiveOps tile (pending/degraded counts), and a new Outbox panel with per-entry **Retry** and **Discard** controls (`POST /api/v1/outbox/{id}/retry`, `DELETE /api/v1/outbox/{id}`). Set `tracker.outbox: false` as a kill switch to restore the previous synchronous write behavior — see `docs/configuration.md`'s `tracker.outbox` row. **Known limitation:** an entry enqueued with no observed `from_state` baseline (currently only the issue-discard path) is exempt from supersede-reconciliation, so it retries until it lands or an operator discards it via the Outbox panel.
- **Critical-path dispatch ordering** (default on): priority band, then transitive dependents, then longest chain, via Tarjan SCC condensation. `dependencies.ordering: critical_path_strict` compares graph leverage ahead of the priority band; `dependencies.ordering: simple` restores the legacy order.
- **Inferred (LLM-detected) dependency edges soft-gate dispatch** — confidence >= 0.7, fresher than 168h, no per-issue operator override, and a known non-terminal source. Tracker-declared blockers remain hard blocks. Kill switch: `dependencies.inferred_gating: false`.
- **Dependency cycles are first-class alerts** (LiveOps tile, Deps-tab banner and red edges, heartbeat). Members stay blocked and are never auto-released. **Escalation** surfaces issues blocked longer than `dependencies.escalate_blocked_after_hours` (default 48).
- **The dependency analyzer is cancellable, timeout-bounded, chunked, and autonomous.** `DELETE /api/v1/deps/analyze/{jobId}` cancels a run; `agent.deps_analyzer_timeout_ms` (default 10 min) bounds it; `agent.deps_analyzer_chunk_size` (default 75) bounds the prompt. Change-driven incremental passes run on a 5-minute debounce with a 60-minute floor (`dependencies.auto_analyze`, default true).
- **Widened tracker dependency parsing.** GitHub now recognises `blocked by/on`, `depends on/upon`, `requires`, and `waiting on/for` plus `#N` lists as hard edges. Linear sub-issues gate their parent.
- **Per-issue inferred-blocker overrides** via `POST`/`DELETE /api/v1/issues/{identifier}/deps-override`, surfaced in the dashboard Deps tab.
- **Dispatch-pressure telemetry**: each tick records whether dispatch was slot-bound or dependency-bound, surfaced in the dashboard status strip.
- **JSON structured logging** via `--log-format=json`; stderr logging is no longer lost when the TUI does not start.
- **Tracker rate limits are now waited out, not fatal.** HTTP 429 responses are retried with a bounded, `Retry-After`-aware backoff (both RFC 9110 forms), capped at 4 retries and 60s per wait and abandoned on shutdown. GitHub signals rate limits with 403 rather than 429 for both its primary and secondary limits, so those are recognised too — by an exhausted `x-ratelimit-remaining` or a `retry-after` header, never by a bare 403, which stays a genuine authorization failure and is not retried. Previously a 429 failed the call outright, so the moment a tracker's budget ran out *every* operation failed — including the state transitions and comments that would have drained the queue and stopped itervox asking for more.
- **The dependency audit refreshes in batches on Linear.** Rows carrying an issue ID resolve in a single `FetchIssueStatesByIDs` request instead of one request each (GitHub has no batch endpoint, so it still fetches per issue); the audit reads only blockers, identity and state, all of which the batch query returns. This was the largest per-issue consumer of the tracker budget (~28% of Linear traffic in issue #42's incident). Identifier-only rows still fetch individually, and an ID absent from a batch response is confirmed by a single authoritative fetch before its row is retired.
- **Stacked worktrees** (`dependencies.stacked_prs`, default `false`). When an issue has exactly one live, identified blocker, its worktree is branched from that blocker's branch instead of `workspace.base_branch`, so the work starts from the blocker's commits rather than duplicating them. Opt-in and best-effort: several live blockers give no unambiguous base, and a blocker branch that does not exist locally falls back to `base_branch` rather than failing the dispatch. The pull-request base is set from the blocker since v0.2.2 (#73).
- **`itervox doctor` validates agent commands.** Every enabled profile's binary is checked against `PATH`, and doctor exits non-zero naming the profile when one is missing. This catches the common case of a tool installed under a version manager (nvm, asdf), whose bin directory is on `PATH` in an interactive shell but not in the environment the daemon was started from — previously visible only as a runtime "command not found" buried in the log.
- **Write priority under tracker rate limits** (`polling.rate_limit_reserve_percent`, default 10). Reads and writes drew on one request budget, and the polling loops scale with the number of stuck issues — so polling could exhaust the hourly budget early, after which every state transition, comment and dependency audit failed. Unsticking an issue requires a write, so reads starved the operations that would have drained the queue. Below the reserve, Itervox now sheds **polling** reads (the candidate poll and the input-required reply check) while still admitting writes and the input-resume fetch. Set `0` to disable; adapters that report no rate-limit counters are unaffected (the check fails open).
- **Pause reasons.** `itervox` now records WHY an issue is paused — `user_cancelled`, `user_dismissed_input`, `retries_exhausted`, or `transition_failed` — and persists them across restarts. Previously a completion-state write that failed was recorded identically to a deliberate user cancel, so an operator could not tell which pauses were safe to resume and a recoverable infrastructure failure sat waiting on a human who had no way to know.

- **Graceful drain on `SIGTERM`/`SIGINT` (CORE-057).** Admission stops across every path (dispatch, retries, pending-input resumes, automations, reviewer, and the HTTP `resume`/`reanalyze`/`ai-review`/`provide-input` controls → `409 draining`); `/api/v1/ready` reports `503` with a new `draining` field; in-flight turns finish on an uncancelled context; the daemon exits once they end, at `--shutdown-grace`, or on a second signal, after the event loop has recorded the exits, flushed its ledgers and joined its workers.
- **Drain-then-reload for operator edits to `WORKFLOW.md` (CORE-057).** Replaces reload-and-cancel. Documented under "Daemon lifecycle" in the configuration reference.
- **`ITERVOX_SERVER_HOST`, `ITERVOX_SERVER_PORT` and `$PORT` bind overrides (CORE-058)**, validated at load; the listening log line names the source that won.
- **`--log-format json` applies to stderr when no terminal is attached (CORE-059)**, through the same secret redaction as the log file. The TUI and interactive terminals keep text.
- **`itervox doctor --deploy` (CORE-063):** `[ok]`/`[warn]`/`[fail]`/`[skipped]` lines for claude and codex credentials (one skipped line per SSH host), `gh auth status`, a `git push --dry-run` push-auth probe, a read-only tracker API call (Linear `viewer`, GitHub repo permissions) and the daemon's `/api/v1/ready`; exits `1` on any failure. No HEARTBEAT age check (it is not a liveness signal).
- **Official container image (CORE-060).** `deploy/docker/Dockerfile` is a three-stage build — web bundle (pnpm), Go binary with the bundle embedded, `debian:bookworm-slim` runtime with git, gh, ssh and tini — running as uid 10001 with `HOME=/data`, `ITERVOX_SERVER_HOST=0.0.0.0` and `ITERVOX_LOG_FORMAT=json`; the claude/codex CLIs are opt-in (`--build-arg INSTALL_AGENT_CLIS=true`). The entrypoint clones `ITERVOX_REPO` once into `/data/repo` and afterwards reuses it (fetch + fast-forward only), feeds `GH_TOKEN` to git through an environment-reading credential helper, and redacts URL credentials from its own and git's output. `HEALTHCHECK` probes `/api/v1/health` (liveness) — not `/ready`, which is 503 for a whole drain. `deploy/docker/docker-compose.yml` sets `stop_grace_period: 300s` for the image's `--shutdown-grace 240s`; `.github/workflows/docker-publish.yml` pushes `ghcr.io/<owner>/itervox` on release tags only, with `permissions: {}` at the top and `contents: read` + `packages: write` on the job.
- **Secret-manager fetch for systemd (CORE-061).** `deploy/lib/fetch-secrets.sh` (the unit's `ExecStartPre`) reads `ENV_NAME=secret-name` pairs from `ITERVOX_SECRETS_MAP` (plus the older per-key variables) from GCP Secret Manager, AWS Secrets Manager or Azure Key Vault and writes `/run/itervox/env` with systemd EnvironmentFile quoting, mode 0600, through an atomic rename; it never prints a value, and a failed fetch leaves the previous file in place. `make deploy-test` runs `deploy/lib/fetch-secrets_test.sh`, which stubs `gcloud`/`aws`/`az` and round-trips values with spaces, `=`, `#`, both quote kinds, backslashes, `$`, backticks and newlines through a port of systemd's parser.
- **Persistent data disk and HOME relocation in `bootstrap.sh` (CORE-062).** `--data-disk <device>` mounts a persistent disk at `--root` by `UUID=` in fstab (`defaults,nofail,x-systemd.device-timeout=30s`), formatting it only when `blkid -p` finds no signature at all; an existing filesystem is reused, and a partitioned or unreadable disk, a conflicting fstab entry or a non-empty mount point over an existing filesystem is refused before anything is written. The service account's HOME is `<root>/home`, so every state root — `~/.itervox/workspaces`, `~/.itervox/logs/<project>/` (history, queue, breaker, session and `api-token` files), `~/.claude`, `~/.codex` — lands on the disk. The provision scripts attach the disk under a stable name and print the path. `deploy/bootstrap_test.sh` (in `make deploy-test`) covers it with stubbed `blkid`/`mount`/`mkfs.ext4`. Bootstrap now ends by running `itervox doctor --deploy` (reported, not fatal).
- **Release archives ship `deploy/` (CORE-064).** Every `itervox_<os>_<arch>.tar.gz` now contains the whole `deploy/` tree with its paths intact (bootstrap, systemd unit, Caddyfile, provision scripts, `lib/`, `docker/`, `monitoring/`) next to the binary, `LICENSE`, `README.md` and `CHANGELOG.md`, so a VM can be bootstrapped from the release tarball alone.

- **Idempotent tracker comments.** Every outbox comment carries a client-generated UUIDv4 key. On a retry, the flusher first asks the tracker whether a comment with that key already exists and marks the entry delivered instead of posting it again; an unanswerable lookup defers the entry rather than posting blind. Linear sends the key as the comment's own id (`CommentCreateInput.id`) and looks it up by id, archived comments included; GitHub embeds it as a hidden `<!-- itervox:ck:<key> -->` marker and scans the newest comments on the issue (GitHub returns issue comments oldest-first).
- **Rate-limited outbox entries wait for the tracker's published reset.** A write rejected by a rate limit is deferred to the reset instant plus up to 5s of jitter, is counted separately from real failures (`rate_limited_attempts`), and never raises the **degraded** badge. The flusher skips its tick — and stops mid-tick — while a rate-limit window is open, so it sends no requests that are known to fail.
- **Rate-limit visibility in the dashboard.** Outbox rows show an amber **rate limited until HH:MM** chip alongside (not instead of) the degraded badge, and the LiveOps strip shows one fleet-level **Tracker rate limited until HH:MM** chip. The snapshot's `outboxEntries[]` rows gain an optional `rateLimitedUntil` (RFC 3339) field.
- **Input-required questions and replies go through the write-ahead outbox.** The agent's question and the operator's dashboard reply are now queued durably like every other tracker write: they survive a restart, are never posted twice, wait out tracker rate limits, and the question is always delivered before the reply.
- **Post a comment from the dashboard.** The issue detail slide has a comment composer; comments go through the write-ahead outbox (`POST /api/v1/issues/{id}/comment`, `202` when queued) and behave like comments typed in the tracker, though they are posted under Itervox's tracker identity.
- **`deploy/bootstrap.sh` installs `gh` and `codex`, and sets up repo access and git identity.** It now installs the GitHub CLI and `@openai/codex` on both apt and dnf hosts, establishes repository access *before* the initial clone (an SSH deploy key for `git@`/`ssh://` URLs, or `gh auth setup-git` with `GH_TOKEN` for `https://` URLs) instead of letting a keyless clone abort the script, and sets an explicit git identity via `--git-name`/`--git-email` (defaulting to `itervox-bot`) rather than guessing an operator identity. The `.env` scaffold gains `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY`, and `GH_TOKEN`. `bootstrap.sh` also gains `--dry-run` and `--dry-run-network` flags for CI smoke testing (CORE-018).
- **Web: destructive actions now require confirmation.** "Cancel"/"Discard" on a running or paused session (Dashboard's Running Sessions table and the issue detail slide) and "clear logs" all route through the existing two-step `ConfirmButton`, which now also disables its trigger while the mutation is in flight and moves keyboard focus to the Yes button (and back to the trigger on Cancel) instead of silently dropping focus to `<body>` (CORE-021).
- **Dashboard: a prominent stale-data banner, keyed off real signal loss.** The header now shows a sticky "Data may be out of date" banner once a snapshot exists but both the SSE channel (keepalives included) and the polling fallback have gone quiet for over 60s — deliberately not keyed off a poll interval, since snapshots are only pushed on change and an idle-but-healthy daemon must not be flagged stale. The banner's age line and the staleness decision are both derived from two new store fields, `lastMessageAt` and `lastSnapshotAt` (CORE-023).
- **Daemon crashes are captured in `crash.log` and reported once in HEARTBEAT.md.** An unrecovered panic on any goroutine previously reached only stderr — journald under the shipped systemd unit, but hidden by the TUI's alt-screen and absent from the rotating log file. itervox now arms `debug.SetCrashOutput` on `<logs-dir>/crash.log` (mode 0600) at startup. The first boot after a crash logs one line (through the redacting handler) and adds `- Last crash: <RFC3339> (full dump: <path>)` to HEARTBEAT.md — timestamp and path only, never panic text, since the dump bypasses log redaction. A `crash.log.marker` baseline makes each crash reported once, not on every start; a `crash.log` over 1 MiB is rotated to `crash.log.1` (one generation kept) at boot. (CORE-007)
- **Background goroutines no longer take the daemon down on a panic, and `make no-bare-go` keeps it that way.** One-shot tasks (tracker comment and state writes, discard transitions, workspace clears) now recover, log with a stack, count the panic, and still publish their completion event — a panicking tracker call inside a discard no longer leaves the issue stuck as "discarding". Long-lived loops (outbox flusher, schedulers, heartbeat, HTTP serve/accept, workflow watcher) log the panic and restore the terminal before failing fast; the orchestrator event loop is deliberately left unwrapped. `make no-bare-go` (part of `make verify`) fails on any production `go` statement without containment unless it is on a reasoned allowlist. (CORE-008)
- **Regression test for the rate-limit auto-switch chain.** `TestE2E_ClaudeRateLimitSwitchesToCodex` drives the real event loop, retries, classifier and backend routing with fake runners and asserts the recovery run reaches the codex runner with a `codex` command; `TestOrchestratorChain_NonRateLimitFailureDoesNotSwitch` pins the no-match path. It does not cover CLI parsing or process launch. (CORE-011)
- **`GET /api/v1/ready`, a readiness probe that reflects whether the orchestrator is working.** `/api/v1/health` only proves the HTTP server answers; a wedged event loop passed it. `/ready` returns 503 when the event loop has not finished an iteration within 3× the poll interval (a tick running a slow tracker call stays fresh for up to 10 minutes), or after three consecutive failed tracker polls, and 200 otherwise. A rate-limited tracker, one or two failed polls, or an invalid `WORKFLOW.md` edit (the daemon keeps running on its last valid config) report `degraded: true` but stay ready. The body is booleans plus `tracker_rate_limited_until`, read from the tracker rate-limit gate. Like `/health` it needs no token and is exempt from the unauthenticated-mode Host guard (CORE-043). Follow-ups: the startup grace now lasts at least 30 seconds, like the idle threshold, so a short `polling.interval_ms` cannot report a daemon that is still starting as not ready (BH-M2-5); and a tick that skips its tracker poll to keep the rate-limit budget for writes now reports `last_poll_ok: false` and `degraded: true`, where it kept showing the last real poll's result (BH-M2-6).
- **Opt-in Prometheus metrics at `GET /metrics`.** Set `server.metrics.enabled: true`. The endpoint needs the same bearer token as the API and answers 404 when disabled. It exports running workers and capacity, worker exits by reason, tracker HTTP calls by outcome, recovered goroutine panics, dropped orchestrator events, failed ledger writes, dispatch pressure, outbox depth (degraded and rate-limited), the tracker rate-limit gate's reset (`itervox_tracker_rate_limited_until_seconds`, which nothing outside the outbox flusher read before), consecutive poll failures and the last tracker error. No series carries an issue identifier, and a scrape never waits on a settings save. Written without a Prometheus client library (CORE-045).
- **The last tracker failure is visible.** A failed tracker poll (outage or rate limit, with the published reset) or a failed move to the failed state is recorded and shown on HEARTBEAT.md's "Last error" line, on `/api/v1/state` as `lastTrackerError`, and in `/metrics`; a successful poll clears a poll failure. When nothing else is wrong, "Last error" also names the degraded outbox entry that failed most recently (outbox rows now carry `lastFailedAt`) (CORE-044).

- **A Recent failures panel on the dashboard.** Worker failures and stalls, tracker poll outages and failed tracker moves, failed runtime-ledger writes, outbox delivery failures, recovered goroutine panics and dashboard errors are now collected in one list of the last 100, newest first, with repeat counts and a link to the issue. The same list is on `/api/v1/state` as `recentFailures` (always an array). Messages name the kind of failure and are redacted; agent output and prompt text stay in the issue log. Rate limits are not listed as failures. The list survives a `WORKFLOW.md` reload but not a restart (CORE-046). Follow-ups: a tracker outage whose error text changes on every poll (a rotating address or request id) filled the list with one entry per poll and pushed every other failure out in about 50 minutes; tracker poll failures are now one entry with the latest message and a running count (BH-M2-2). A failure reported after the daemon's main loop stopped was lost without being counted; it is now counted as dropped (BH-M2-4).
- **Dashboard errors reach the daemon.** A crash caught by the dashboard's error screens, an uncaught browser error or rejected promise, and snapshot schema drift are reported to the new `POST /api/v1/client-errors` (authenticated, 8 KiB cap, rate-limited), logged by the daemon with redaction, counted in `itervox_client_errors_total`, and added to Recent failures. The dashboard sends only the message, kind, page path and a trimmed stack, dedupes repeats for a minute, and sends at most 10 reports a minute (CORE-048). Follow-up: the daemon-side rate limit was one bucket shared by every dashboard tab and reset by every `WORKFLOW.md` reload. It now keeps a bucket per client address (20 reports, then one every 3 s) under a daemon-wide cap (60, then one a second), and the buckets survive reloads.
- **Typed vendor limit signals from the agent stream.** Claude's `rate_limit_event` (status, reset time, 5-hour/weekly window), `system/api_retry` (vendor retry delay; advisory only — the CLI is still retrying) and the result's `api_error_status` are parsed instead of dropped, and Codex's top-level `error` event and error items are no longer skipped: its usage-limit message ("You've hit your usage limit … try again at 3:04 PM") is classified with the reset time. The log now names these events (`vendor limit reached`, `api retry`) instead of logging every Claude `system` event as "session started". (CORE-050)

- **Backend-wide circuit breaker (CORE-053).** One breaker per agent backend and worker host (`claude`, `codex@build-1`): a usage limit, or repeated `api_retry` rate limits, open it; every admission path (worker, retry, reviewer, automation, input-required resume) checks it after the backend is resolved, and a held issue shows `backend_limited` as its "why idle" reason. When the reset passes, exactly one probe run is dispatched; its success closes the breaker, a new limit reopens it.
- **Declarative `agent.backend_fallback` (CORE-054).** `chain`, `profile_map` (with a `default` key for `agent.command`), `on_unmapped`, `default_cooldown_minutes`, `min_dwell_minutes` and `switch_back: at_reset | on_success | manual`, validated at load (unknown, disabled or wrong-backend targets are rejected). A limited target is rerouted to its counterpart profile on the next healthy backend, including for reviewers (per run). ### Changed (breaking)

- **Bearer-token auth is now on by default on every bind, including loopback (#48).** Previously the daemon only auto-generated `ITERVOX_API_TOKEN` and installed bearer-token middleware when `server.host` was a non-loopback address. That gate was the wrong signal: a loopback bind (`127.0.0.1`) sitting behind a reverse proxy, ngrok, Piko, or another tunnel is exactly as reachable from outside as a non-loopback bind, and the daemon has no way to detect that from inside the process. As of this release, the API requires a bearer token by default on **all** binds; unauthenticated local scripting must either read the token (from stderr, `.itervox/dashboard_url`'s sibling startup log line, or a pinned `ITERVOX_API_TOKEN` in `.itervox/.env`) or explicitly opt out via `server.allow_unauthenticated: true`.
- **`server.allow_unauthenticated_lan` renamed to `server.allow_unauthenticated`.** The flag is no longer LAN/non-loopback-scoped — setting it to `true` disables auth entirely on every bind. The old key still parses as a deprecated alias (with a startup `slog.Warn`); the new key wins if both are set in the same `WORKFLOW.md`. Update `WORKFLOW.md` and any templates/examples to use the new key.
- `GET /api/v1/health` remains the only auth-exempt route — unchanged behavior, but corrected in docs (README, `docs/configuration.md`) which previously and incorrectly described it as `GET /health`.
- **`server.port` defaults to a fixed 8090** instead of an ephemeral port — see upgrade note 6.

### Changed

- **The HTTP socket survives config reloads.** The listener binds once, above the reload loop, and is rebound only when the resolved address actually changes — so editing an unrelated setting no longer drops in-flight requests, and the dashboard URL stays stable. Open SSE streams are closed on a reload, and the dashboard reconnects to the new configuration in about a second. WORKFLOW.md edits debounce into a single reload.
- **Linear workflow-state UUIDs are cached**, so a state transition costs one request instead of two; `FetchIssuesByStates` honors the runtime project filter.
- **GitHub blocker states are cached for 5 minutes** — probe-measured at ~480 requests/hour against ~4,800 uncached at 40 refs.
- **The dependency audit's synchronous tracker fetches moved off the event loop** (batched, throttled, watchdogged) and gained a staleness TTL (`agent.dependency_audit_refresh_interval_ms`, default 10 min).
- **The input-required replay cache survives across ticks**, removing a per-entry re-fetch every 15 seconds.
- **Multi-reviewer fan-out actually runs.** `agent.reviewer_profiles` was documented as running each reviewer sequentially and independently, but `ReviewerProfileChain` truncated the chain to one entry, so a multi-reviewer config silently ran only the first — the documentation promised behaviour that did not ship. The truncation is removed and two lifecycle defects that gated it are fixed: (1) the chain never advanced, because the handler identified a reviewer only via `state.Running`, which reconciliation deletes first when `tracker.completion_state` moves the issue terminal; it now recovers the identity from the reviewer-injected profile map, which reconciliation does not touch. (2) the workspace was auto-cleared after each reviewer rather than after the quorum, so the next reviewer read a verdict from a torn-down worktree; the clear decision now also consults whether a chain is still in flight.
- **Stacked branches are restacked when their blocker lands.** With `dependencies.stacked_prs: true`, a dependent's worktree is replayed onto `base_branch` once its blockers reach a terminal state, so a stack no longer drifts behind subsequent merges. Three cases are refused rather than forced: a **running** dependent is skipped (rebasing a worktree an agent has checked out moves `HEAD` under a live process), a **dirty** worktree is skipped (that work is unpushed), and a **conflict** aborts the rebase — leaving the branch byte-identical — and parks the issue in `input_required` with the reason. Since v0.2.2 the dependent's pull request is retargeted to `base_branch` as well (#73).
- **`agent.profiles.<name>.permission_mode`** selects the approval/sandbox flags a profile's turns launch with: `bypass` (default, the long-standing `--dangerously-*` behaviour) or `sandbox` (`--permission-mode acceptEdits` for Claude, `--sandbox workspace-write --ask-for-approval never` for Codex). Both stay non-interactive, which is not optional — itervox is headless, so a mode that can pause for approval hangs the turn until the timeout kills it. An unrecognised value warns and falls back to `bypass`. Note the asymmetry: Codex genuinely confines filesystem writes to the workspace, while Claude has no equivalent sandbox — `acceptEdits` bounds what the agent is asked to confirm, not what the process can reach.
- **Tracker rate-limit backoff is coordinated across the process**, not rediscovered per call. A 429 records the window once in a shared gate; every other caller waits on it instead of spending its own request to learn the same thing and then resuming on its own schedule (which put N simultaneous probes on the tracker at the end of each window). Writes are admitted ahead of reads when the gate lifts, matching `polling.rate_limit_reserve_percent`'s intent. Bounded and fail-open: a never-clearing gate degrades the daemon rather than wedging it.
- **Comment-bearing tracker reads are now batched** (issue #42's remaining ~56%). The tracker-reply check, the pending-input resume, and the input-required replay each cost one request per blocked issue per tick, and none could use `FetchIssueStatesByIDs` because all three read comments, which that query omits. A new optional `tracker.DetailBatcher` interface adds `FetchIssueDetailsByIDs`, implemented for Linear via a batched GraphQL query that carries comments. Measured over a 40-issue input-required backlog: **40 requests → 8, a 5.0x reduction**, with per-tick cost now fixed at one request regardless of backlog size.
  - The GitHub adapter deliberately does **not** implement it. GitHub's REST API cannot batch, so the method could only fan out per-issue calls — and its `FetchIssueDetail` costs two requests, so a "batch" of N would cost 2N while presenting itself as one cheap call. Callers fall back to per-issue, which is honest about the cost.
  - The prefetch is filtered to cache misses. Prefetching unconditionally would have spent one request on every steady-state tick, where a blocked backlog with its rules already fired costs zero — reintroducing the per-tick waste through the fix for it.

- **Deployment docs: platform tier matrix and front-door guidance corrected (CORE-065).** The deployment guide now has a stop-timeout table for the drain, an official-image section, and a tier matrix that matches what the daemon does: Cloud Run *services* (not worker pools, which have no ingress) are experimental because Cloud Run allows only 10 s between `SIGTERM` and `SIGKILL`; the 25 s SSE keepalive applies to `/api/v1/events` only (the log streams have none); `server.allowed_hosts` matters only with `allow_unauthenticated`. The Vercel page no longer suggests hosting only the web UI there — the daemon sends no CORS headers, so that cannot work. `deploy/monitoring/README.md` documents JSON stderr (CORE-059) and `/ready`'s `draining`; the site API reference mirrors `docs/api.md` for `/ready`, `409 draining` and `POST /settings/models/refresh`.
- **Tracker-state, project-filter and model-list saves no longer reload `WORKFLOW.md` (CORE-160).** The tracker clients take new state lists in memory (`tracker.StateListSetter`), the project filter is applied to the Linear client, and `agent.available_models` has a runtime setter (now on the cfgMu list). All three are self-writes under the settings-generation fence, so saving them never touches an in-flight turn. `POST /settings/models/refresh` can answer `503 settings_reloading`; an omitted/empty project filter now leaves the live filter at "all issues", matching the commented-out `project_slug` on disk.

- **`agent.inline_input: true` now does what it says.** The tracker becomes the only place a human can reply to an input-required agent: the dashboard reply box is hidden and `POST /api/v1/issues/{id}/provide-input` returns `409 inline_input_enabled`. - **Web cleanup (CORE-083).** Removed state that nothing read (`dashboardSearchVisible`, the `tokenSamples` window recomputed on every snapshot), two unused helpers, an unreachable empty state, about 280 lines of CSS for libraries the dashboard does not use (FullCalendar, Swiper, jVectorMap, simplebar), and two unused lint plugins from `devDependencies`. ### Fixed

- **Two daemons could start on the same project.** The single-daemon guard was read-check-write, with 73 lines of startup between deciding "nobody is here" and recording "I am here" — both could pass and share one `.itervox/`, interleaving `HEARTBEAT.md`, the outbox, and the automation queue. The claim is now atomic: content is written to a temp file and hard-linked into place, so the pid file is complete at the instant it becomes visible. (`O_CREATE|O_EXCL` alone was not enough — it creates the file empty, and a racing claimant reads the zero-length file, concludes "malformed, therefore stale", deletes it, and claims. A 24-way concurrent test produced nine winners.)
- **Skill analytics ignored `--logs-dir`.** The adapter computed the *default* per-project logs path regardless of where the daemon was actually told to write, so an operator who passed `--logs-dir` got analytics that read a directory nothing was writing — rendering empty rather than erroring, so the failure was silent. The resolved directory is now threaded onto the adapter (derived from the log file `run` already receives, so the one place that resolves the path stays authoritative). Without the flag, behaviour is unchanged.
- **A hallucinated self-referential dependency could park a real issue indefinitely.** The analyzer's identifiers were validated against the fetched issue set, but nothing checked that the claimed *relationship* was possible, so an LLM-emitted `ENG-7 blocks ENG-7` reached the sidecar. A self-edge is a single-node strongly connected component, which the tick graph reports as a dependency cycle — and cycle members stay blocked, with nothing to auto-release them. Self-edges are now dropped both at the analyzer boundary and when loading a sidecar written before the guard existed. Rejecting self-reference cannot discard a genuine dependency, unlike quote-matching evidence against issue bodies, which was considered and rejected (analyzer evidence is usually paraphrase, so it would drop real edges in bulk).
- **Auto-review could spawn agents without bound.** With `tracker.completion_state` set, a successful worker moves its issue terminal; reconciliation then stops the run and removes it from the live set, so the run's own exit event arrived with no live entry. That was read as "a plain worker succeeded", which dispatched a reviewer, which was stopped the same way — a loop nothing broke while the issue stayed terminal. The eligibility check now fails closed on an unknown run. Measured before the fix at 23-30 agent runs in 1.5s against an expected 2.
- **The write-ahead outbox discarded its own completion transitions.** The completion path enqueues the session comment ahead of the state transition for the same issue, so the comment flushed first and bumped the tracker's `updated_at` without changing state — which reconciliation read as a human edit and dropped the transition, leaving the issue active and eligible for re-dispatch. Entries now record the state observed at enqueue time, and reconciliation requires an actual state change.
- **A malformed persisted outbox entry could wedge an issue's write queue silently.** Entries are validated on load, not only on enqueue, and an undeliverable entry now accrues attempts so it backs off and surfaces as degraded instead of retrying at full tick rate behind a healthy-looking badge.
- **Incremental dependency analysis eroded its own graph.** An inferred edge spanning a changed and an unchanged issue was dropped and could not be re-derived, because the unchanged endpoint never reached the analyzer. With auto-analysis on by default and no scheduled full pass, repeated runs degraded the graph and silently un-gated dispatch. Boundary-spanning edges now bring their unchanged endpoint into the pass.
- **A cosmetic `server.host` edit could kill the daemon.** The reload path compared the literal `host:port` string, so `127.0.0.1` to `localhost` looked like a move; the new listener bound before the old one closed, collided with itself, and exited via a path that skipped cleanup of `daemon.pid`, `dashboard_url`, and `HEARTBEAT.md` — leaving `itervox doctor` reporting a daemon that had died. Rebinds are now decided on the resolved address and release the old socket first.
- **One transient accept failure could wedge the HTTP listener for the life of the process.** The daemon's accept loop replaced `http.Server.Serve`'s, which backs off and retries temporary errors — without that, a single fd-exhaustion blip (`EMFILE`/`ENFILE`) ended accepts while the socket stayed bound, so the port still showed LISTEN, clients hung, and a config reload could not recover it. Temporary accept errors now retry on net/http's 5ms-doubling-to-1s schedule.
- **A config reload could briefly run two orchestrators against one outbox file.** `run()` waited for the HTTP server when the orchestrator exited first, but returned immediately in the opposite case — which is the one a reload actually takes, since shutting down the HTTP generation is a channel close while the orchestrator is still draining. The reload loop then opened a second `.itervox/outbox.json` handle, and two handles rewriting the whole file each persist can erase one another's durable entries. Both exit paths now wait, with a bounded grace and a warning if it is exceeded.
- **The input-required reply check no longer scales its request rate with the backlog.** It spent one tracker request per stuck issue per tick, uncapped and in randomized map order, so a 19-issue backlog cost roughly 2,280 requests/hour against Linear's 2,500/hour ceiling before any real work (issue #42). It now spends a fixed budget per tick, least-recently-checked first, so cost is constant in backlog size and every entry is still reached within a couple of minutes. The pending-resume path gained the same bound on its failing-fetch retries.
- **The "another daemon is already running" guard actually holds now.** Three gaps closed: it ran *after* the logs directory was created and the rotating handler installed, so a daemon about to be rejected had already written to the live daemon's log file; every per-project path derivation now shares one symlink-resolving helper, so a checkout addressed by two spellings (a symlinked working copy, or `/tmp` vs `/private/tmp` on macOS) no longer gets two separate sets of state — previously the hash-derived logs directory and workspace root differed per spelling, silently abandoning the previous run's queue, audit and worktrees; and the one-shot subcommands that write `.itervox/` state outside the daemon — `itervox init --update` and `itervox deps analyze` — bypassed the guard entirely and now warn that a live daemon owns the same state.
- **A bare clone is no longer reused for a different repository.** `EnsureBareClone` reused `<root>/.bare` on the mere presence of a `HEAD` file, never comparing `remote.origin.url` to the configured `clone_url` — so two projects sharing a workspace root had the second daemon silently operating on the first one's repository, branching from, committing to and pushing the wrong repo. It now verifies the remote (normalising scp-vs-https spellings) and refuses rather than re-cloning, since the existing clone may hold another daemon's live worktrees.
- **`itervox init` no longer scaffolds a colliding workspace root.** It wrote `root: ~/.itervox/workspaces/<repo-basename>`, and because that is explicit it bypassed the per-project default entirely: two checkouts named `api` under different owners shared a root, and every non-git directory shared `my-project`.
- **Skill analytics read this project's logs.** They pointed at the bare `~/.itervox/logs`, which the daemon no longer writes — returning nothing, or another project's leftovers.
- **Projects no longer share state through global directories.** Two collision surfaces, both keyed by values that are only unique *within* one project:
  - `~/.itervox/logs` was shared by every project without a `tracker.project_slug`, and that directory holds `automation_queue.json` — which carries the **dependency audit**. One project's audit rows were restored by another's daemon on every start. Observed live: a Linear project inherited ten `demo-id-*` rows written by an unrelated `kind: memory` run, then asked Linear about issues that had never existed there on every refresh cycle.
  - `workspace.root` defaulted to a single `~/.itervox/workspaces`, and a workspace directory is keyed by issue **identifier** alone. GitHub identifiers are the repo-local issue number, so *every* GitHub repo has a `#1` — two daemons would use the same directory for their respective issue #1, checking out different codebases over each other, and one project's `workspace.auto_clear` would delete another's live worktree mid-run.
- **Malformed issue IDs no longer fail a whole Linear batch.** `issues(filter: {id: {in: […]}})` validates the entire list and rejects the request if any element is not a UUID or `TEAM-123` identifier, so one stale row took down every healthy row beside it. Such ids are now filtered out before the query and confirmed individually instead.
- **A deleted or unknown Linear issue no longer retries forever.** Linear reports an ID it has never seen as a GraphQL error (`Entity not found: Issue`), not as a null result, so it was classified as a transient failure and the dependency-audit row was retained and retried every refresh cycle for the daemon's lifetime. It now maps to the not-found sentinel and the row retires. Only that specific message is treated as permanent — rate-limit and auth errors stay retryable, because the response to not-found is to delete the row.
- **`itervox init --update` creates `.itervox/.env`.** The update path returned after migrating the workflow schema and never reached the code that scaffolds the environment file, so a migrated project was left referencing `$LINEAR_API_KEY` with no file to define it in and the daemon hard-failed startup with `missing tracker.api_key`. The stub is written with `0600` permissions and never overwrites an existing file.
- **Hallucinated dependency edges no longer reach the sidecar.** Nothing validated that analyzer-emitted `source`/`target` identifiers corresponded to real issues, so an LLM-invented pair was written to `.itervox/dependencies.json` and reloaded verbatim on every start. Edges are now validated against the fetched issue set. Validation is against the whole fetch, not the analyzed chunk, so legitimate cross-chunk edges survive.
- **A fatal daemon exit no longer leaves stale liveness files.** `fatalExit` is `os.Exit`, which skips deferred cleanup — so a failed rebind or an invalid config left `daemon.pid`, `dashboard_url` and `HEARTBEAT.md` behind, which are exactly the files `itervox doctor` and `itervox status` read to decide a daemon is alive. The daemon died while leaving evidence it was running.
- **`itervox doctor` no longer warns on a healthy daemon.** Its port-collision check keyed off "`server.port` is set", but that field is always populated now that the port defaults to 8090 — so every daemon reported its own listening socket as a collision, with a warning and exit 1. It now compares the holder's PID against the recorded daemon.
- A transient empty tracker fetch can no longer wipe the inferred-dependency sidecar.
- Dependency-analyzer runs report the number of issues scanned, write logs to disk, and report progress.

- **A forced stop records the turn it killed.** When the drain grace expires, a second signal arrives, or a reload's grace runs out, the event loop now outlives its workers (bounded by the 20 s worker-join grace) and consumes their exit events: the killed run lands in history as `cancelled`, its in-flight handoff is renamed `.partial.md`, and the ledgers are flushed after it. Before, every such exit was dropped with `exit event dropped (orchestrator exited)` (M4-close D1).
- **A drain requested before the first poll no longer starts a turn.** SIGTERM during startup (or between two generations) raced the immediate first tick and admitted work about two times in three; `RequestDrain` now closes admission before the tick can run, at every admission point (M4-close D2).
- **`ITERVOX_SERVER_HOST=::` / `::1` / `[::1]` now starts.** The listen address was built with `"%s:%d"`, so every IPv6 value validation accepted failed with `too many colons in address` (M4-close D6).
- **An invalid `PORT` no longer breaks a daemon that sets `ITERVOX_SERVER_PORT`**: only the winning port variable is validated.
- **Log lines emitted before the log handlers are installed are redacted and follow `--log-format`.** The stale-PID reclaim and the invalid `--log-format` warning used Go's default text logger — plain text on a JSON-logging container, and not behind the secret redaction (M4-close D8).
- **A signal between two generations (the reload back-off) stops the daemon at once** instead of first starting another generation.
- **`itervox doctor --deploy` no longer runs the repository's pre-push hook.** The push-auth probe's `git push --dry-run` now passes `--no-verify`; a lefthook/husky suite ran as a side effect of a "read-only" probe and a failing hook reported as `[fail] git push auth` (M4-close D9).
- **`bootstrap.sh`: `GH_TOKEN` is no longer in any command line or in `--dry-run` output, and a private HTTPS clone receives it.** It is passed with `sudo --preserve-env=GH_TOKEN` to `gh auth setup-git`, the clone and the deploy doctor; before, `sudo … env GH_TOKEN=…` exposed it in the process list and the dry-run echo, while the clone itself (whose credential helper reads `GH_TOKEN`) ran without it. `--git-name` with a quote no longer breaks (or executes) the git-config step; `.itervox/.env` is created `0600` instead of being chmod'ed after the API token was written; an unreadable data disk (`blkid -p` exit 2 with an error) is refused instead of being formatted as blank (M4-close BH-M4-4/5, D10).
- **`aws/provision.sh` creates the data volume in the instance's availability zone** (read from `Placement.AvailabilityZone`) instead of `${REGION}a`, which failed with `ZoneMismatch` whenever EC2 placed the instance elsewhere; it waits for the attachment, drops the redundant `modify-instance-attribute`, and removes the instance and volume it created when a later step fails (M4-close BH-M4-6).
- **The container healthcheck no longer probes port 0** when `PORT=0` / `ITERVOX_SERVER_PORT=0`: it reads the bound port from `dashboard_url` (M4-close D7).
- **A backend breaker can no longer park a backend for years.** The reset time is capped by where it came from (5h15m for the five-hour window, 7d1h for weekly windows, 24h otherwise; 6h for resets read from text; 1h for `api_retry` throttles), a persisted far value is capped again on load, and a held retry never waits past the 6h retry cap.
- **A usage-limit retry waits for the reset, not for a leftover `api_retry` delay.** A quota signal no longer inherits the seconds-long `retry_delay_ms` of an earlier `api_retry` event.
- **A Claude result line with `"api_error_status":"429"` (or `429.0`, or a string `resetsAt`/`retry_delay_ms`) is no longer dropped.** These limit fields are decoded tolerantly; before, the whole line failed to parse and the turn's result was lost.
- **A Codex "try again at 3:04 PM" from an SSH worker is treated as an unknown reset** (bounded cooldown + probe) instead of being read in the daemon's time zone.
- **Backend chips and the TUI show the date of a reset that is not today**; the TUI LIMITS row is clamped to the terminal width. An api_retry signal dropped on a full event queue is offered again; breakers for removed SSH hosts or unused backends are pruned; the held count ignores stale holds; the issue-detail backend control no longer carries an error from the previous issue.

- **The dashboard no longer freezes silently when it cannot read the daemon's snapshot.** A snapshot that failed validation used to be dropped without a word in production, so the page kept showing old data. Three failures in a row now show a "Dashboard cannot read daemon updates" banner (cleared by the next good snapshot) and report the drift to the daemon. A status or mode value the dashboard does not know (for example a new dependency-analysis mode) no longer rejects the whole snapshot: that one field falls back to a safe default and the fallback is reported. Values you can save back — an automation's trigger (with its trigger and policy settings), match mode and backend override, and a profile's allowed actions — are instead shown read-only as "Unknown … (from a newer server)" and sent back unchanged when you save, so an older dashboard never rewrites config it does not understand (CORE-047).
- **A settings save that races a `WORKFLOW.md` reload is retried instead of failing.** The daemon refuses such a save with `503 settings_reloading` without writing anything; the dashboard now waits the `Retry-After` time, sends it once more and refreshes, so the operator no longer sees a spurious "failed to save" (CORE-170).
- **Saving settings no longer kills running agents.** Every dashboard or TUI settings save (workers, reviewer, automations, auto-clear, failed state, retries, switch caps, SSH hosts, dispatch strategy, inline input, profiles, dependency analysis mode) rewrote `WORKFLOW.md`, and about 3–5 seconds later the file watcher treated that as an edit and reloaded the daemon — cancelling every in-flight agent turn, although the new value was already live. The watcher now recognises the daemon's own writes and does not reload for them. Any edit made outside this daemon still reloads: a hand edit, another `itervox` command, or a hand edit that lands in the same few seconds as a settings save. Three saves still reload, because part of what they change is only picked up on a reload: the tracker's active/terminal/completion states, the project filter, and a dashboard model refresh. What a reload does to running turns is unchanged. A side effect: a leftover `dependencies.auto_analyze` line no longer logs its deprecation warning on every settings save, only on real reloads. (CORE-116) Follow-ups: a settings save that landed during a reload (after the old watcher stopped and before the new one started) made the NEXT settings save reload the daemon anyway; the watcher now starts from a clean slate, and an edit made outside the daemon between two of its saves still reloads (BH3). Two settings saves at the same time (for example two dashboard tabs, or the TUI and the dashboard) could leave `WORKFLOW.md` and the running config on different values, and with no reload nothing brought them back in line; each save now writes the file and applies the value as one step, and a save whose undo also fails is logged as an error and reported to the caller instead of being dropped (V4). Two gaps remained around a reload. An edit made while the daemon was starting a reload, after it read `WORKFLOW.md` but before the watcher started, was never picked up; the watcher now starts from the exact file the config was read from, so that edit reloads. A settings save still in progress from before a reload could write `WORKFLOW.md` after the reloaded daemon had read it, leaving the file and the running config different with nothing to fix it; such a save is now refused with `503 settings_reloading` (nothing is written, retry it), and the daemon waits for a save already writing to finish before it reads the file (M1-close C2). Every settings endpoint returns that 503, including the tracker failed-state setting, which had answered 400, and the Skills "fix" action that disables a profile, which had answered 500 (D2, E1). A hand edit that ends up back on exactly the bytes the daemon had read, with a settings save in between, now reloads when it all happens before the watcher starts (D4, E2). More than 16 settings saves in a row with no 2-second pause, for example holding the TUI worker +/- key, no longer cause one needless reload; past 4096 saves without a pause the daemon reloads once rather than risk missing a hand edit (D5, E3).
- **`itervox init --update` and `itervox models refresh` could silently overwrite a settings save made by a running daemon, and vice versa.** The `WORKFLOW.md` edit lock only worked inside one process. Every read-modify-write of `WORKFLOW.md` — the daemon's settings writers, `models refresh`, and `init --update`'s schema migration and `--server-port` rewrite — now also takes an `flock` on a `.WORKFLOW.md.lock` file next to it, so edits from separate processes are applied one after another instead of one clobbering the other. See upgrade note 12. (CORE-149) `itervox init --force`, which overwrites `WORKFLOW.md`, now takes the same lock (V5).
- **Duplicate tracker comments.** A comment the tracker accepted but whose response was lost or timed out was re-posted on every retry.
- **Linear rate limits were not recognised.** Linear signals a rate limit as HTTP 400 with a `RATELIMITED` GraphQL error code, not a 429, so it failed as a plain 400: no retry, no fleet-wide coordination, and the outbox retried blind on its own backoff. Linear's `X-RateLimit-*-Reset` headers (epoch milliseconds) are now honoured.
- **"Writes go first" had no effect on Linear.** Every Linear call is an HTTP POST, so reads and writes looked identical to the rate-limit gate. Linear requests are now classified from the GraphQL operation type, so comments and state changes are admitted ahead of polling reads when a rate limit lifts.
- **A GitHub secondary rate limit could stall GitHub calls for up to an hour.** GitHub sends `X-RateLimit-Reset` on every response; it was being used even for a secondary limit, where `Retry-After` governs. The reset is now honoured only once `X-RateLimit-Remaining` reaches 0.
- **A success on the last in-call retry was reported as a rate limit.** The retry helper now classifies the final response instead of assuming it failed.
- **Rate-limit windows are capped at 2 hours**, both on the fleet-wide gate and on the reset instant stored on each outbox entry, so a malformed reset header can neither stop tracker writes nor park a single entry for longer than that.
- **A human reply to an *earlier* question on the same issue could resume an agent that had asked a new question whose comment had not reached the tracker yet.** Questions are now matched by a unique key rather than by position whenever the outbox is enabled.
- **A reply written before the agent's question reached the tracker was never treated as the answer.** With the outbox enabled, a comment created after the question was queued now resumes the agent whether the question has landed yet or not, and even if it ends up ordered above the question. Previously the operator had to reply again once the question appeared.
- **An agent turn could hang after a read timeout or an oversized output line.** On an idle read timeout or a scanner error, the Claude and Codex runners now kill the agent subprocess immediately instead of leaving it running until the (up to one hour, or disabled) turn timeout eventually fires, and the turn is now reliably reported as failed with a diagnostic message instead of sometimes looking like a clean session end (CORE-001).
- **A turn that exceeded `agent.turn_timeout_ms` is now reported as failed instead of as a clean session end.** An operator pause or daemon shutdown (a cancelled turn) still reports no diagnostic text, unchanged from before (CORE-001).
- **The per-issue live log stream stopped delivering new lines after the first 500.** The dashboard's log viewer tracked its position as a plain count into the 500-line ring buffer, so once that many lines had been sent it never advanced again even though the agent kept producing output. It now resumes by a sequence number that survives the buffer sliding forward; if a client's connection lagged far enough behind that some lines were permanently evicted (or the daemon restarted), it is told about the gap and replayed the current window instead of silently stalling (CORE-003).
- **`deploy/gcp/provision.sh` printed an IAP tunnel to port 8090 that could never work.** The firewall rule only opened tcp:22, and itervox binds loopback only, so the documented `start-iap-tunnel 8090` step could never reach the daemon. Cloud NAT was also only echoed as text rather than created, and the firewall-rule step swallowed all errors. The script now tunnels SSH over IAP with a local `-L 8090:localhost:8090` forward, creates the Cloud Router/NAT idempotently, and no longer swallows errors (CORE-015).
- **`deploy/bootstrap.sh` failed outright on Amazon Linux 2023.** The dnf branch's `curl`/`gnupg2` package list conflicts with AL2023's preinstalled `-minimal` packages, and Node.js/Caddy installation only had an apt path, so the AWS-provisioned distro could not bootstrap at all. The dnf branch now installs with `--allowerasing` and gets its own Node.js (NodeSource RPM) and Caddy (Cloudsmith RPM repo) install paths; the AWS AMI selection now follows the requested instance type's architecture instead of hard-coding x86_64 (CORE-016).
- **`deploy/azure/provision.sh` never provisioned egress and printed an unsupported Bastion tunnel.** The VM subnet got no NAT gateway, and the documented `az network bastion tunnel ... --resource-port 8090` step is explicitly unsupported by Bastion (it only relays SSH/RDP, not arbitrary web servers); `AzureBastionSubnet` and Bastion's public IP were also never created. The script now creates a NAT gateway idempotently (never replacing an existing subnet association), documents Tailscale as the default access path, and — when Bastion is used — tunnels SSH with `--enable-tunneling` and forwards 8090 locally over that tunnel instead (CORE-017).
- **Deploy and site docs corrected several stale claims (CORE-019).** Pages had said itervox "installs NO auth middleware" or described an "auth gap", that journald "goes quiet" and neither log sink is JSON (both already fixed by the fanout/`--log-format=json` change), that `claude setup-token` persists credentials to the service account's home directory, that `--log-format=json` also switches headless stderr to JSON, and stated the port-0 default inconsistently with `itervox init`'s actual scaffold. In fact `claude setup-token` prints a one-year token once and saves it nowhere — `deploy/README.md` and the deployment guide now say to copy it into `.itervox/.env` as `CLAUDE_CODE_OAUTH_TOKEN` (the scaffold line is shown), and that only an interactive `/login` on the VM persists to `~/.claude`; and `--log-format=json` applies to the rotating file log only — stderr/journald stayed in charm's human format until CORE-059 made it configurable too. `deploy/README.md` also gained "State roots" and an expanded headless agent-credentials section (Bedrock/Vertex/Foundry via instance identity).
- **Every mention of the dashboard URL and its token now matches what `itervox init` actually scaffolds (CORE-022).** `getting-started.mdx` told every reader to open `http://localhost:8090` even though `init` scaffolds `server.port: 0` (an OS-assigned port); it now explains that omitting `server.port` defaults to 8090 while `init` scaffolds an OS-assigned one, and points at `.itervox/dashboard_url`, the TUI's `w` key, and `itervox doctor`. The same page had said those sources give the dashboard URL including its bearer token — they give the token-free URL; the page now lists where the token actually comes from (TUI `w` key, a terminal's startup stderr, `<logs-dir>/api-token`, or a pinned `ITERVOX_API_TOKEN`). The dashboard's "Cannot reach the Itervox API" banner told the operator to pin `server.port: 8090`, which is only right when `server.port` is omitted — the banner now explains both cases. `itervox init`'s "Next steps" never mentioned `itervox doctor` or how to find the dashboard URL, and `internal/config/config.go`'s `DefaultServerPort` comment claimed 8090 "matches the scaffolded WORKFLOW.md" even though `init` writes an explicit `server.port: 0` — the comment now says so, 8090 remains the real default only when `server.port` is omitted from WORKFLOW.md entirely, and "Next steps" now tells the operator to check `.itervox/dashboard_url`, press `w` in the TUI, or run `itervox doctor`.
- **The web SSE client never reconnected after a clean server close.** `@microsoft/fetch-event-source` resolves and ends the stream for good when its `onclose` callback returns normally — only a thrown error triggers a retry — so a graceful proxy/load-balancer close, or any handler that returns cleanly, silently dropped the dashboard onto a 3s polling fallback for the rest of the page's lifetime. `onclose` now throws (routing into the existing backoff/reconnect path in `onerror`) unless the stream was deliberately aborted by the caller, and no longer double-notifies `onDisconnect` (CORE-004).
- **A11y quick wins: focus ring, reduced motion, `aria-current`, and an inert mobile drawer.** 12 of 20 `outline-none` sites had no replacement focus indicator; a single global `:focus-visible` rule now covers all of them. A `prefers-reduced-motion: reduce` media block zeroes animation/transition durations app-wide. The sidebar's active `NavLink` now carries `aria-current="page"`. Below the `md` breakpoint, the closed mobile nav drawer stayed in the tab order and the accessibility tree (hidden only via `opacity-0`/`pointer-events-none`); it is now `inert` whenever it is not open, without disturbing the existing focus trap while it is open. The daemon now holds an `flock` on `.itervox/runtime/daemon.pid.lock` for its lifetime (already covered by the `runtime/` line of `.itervox/.gitignore`; never delete it while a daemon runs) and marks its pid record with a third `flock` field; a record whose lock is free is stale whatever process owns its pid today, which also fixes a refusal after an unrelated process recycled the pid. A two-field record written by an older version is still refused while its pid is alive and is not ours, so an old daemon running across an upgrade is respected; one holding our own pid is reclaimed. `itervox stop`, `status` and `doctor` read both record shapes. On platforms without `flock` (Windows, not a release target) the old pid-probe guard is unchanged. (CORE-039)
- **A dashboard server wrapped in any middleware kept its SSE streams open through a reload.** The stream closer was found by type-asserting the HTTP handler to the dashboard server, which matches only an unwrapped server, so wrapping it (a logger, a counter) silently left every open stream running until the 5 s shutdown deadline force-closed it. The closer is now passed explicitly. The production handler was not wrapped, so released builds were not affected; this removes the trap. (M1-B1 M3)
- **A rate-limit error could carry a reset far beyond the 2-hour cap.** The fleet-wide gate capped a malformed reset header at 2 hours, but the error handed back to the caller kept the raw instant, so the gate and the error disagreed about the window. The typed error now carries the same capped instant; the per-entry cap in the outbox stays as a second guard. (CORE-117)
- **A tracker call retried a rate limit before the published reset.** When Linear published a reset that fit the wait budget, the in-call retry still followed the 2 s, 4 s, 8 s… ladder and sent requests into a window the daemon had just recorded as closed. The retry now waits for the reset. (CORE-118)
- **A GitHub `Retry-After` longer than 60 seconds was cut to 60 seconds.** The call slept 60 s and sent again inside the window GitHub had declared (up to about four minutes of that per call, on the poll path too), and the error that reached the outbox carried no reset. A `Retry-After` is now treated as a published reset: past the 60 s wait budget the call fails fast, and the gate and the outbox both wait the full window. (CORE-119) A `Retry-After` of about 292 years or more (9223372037 seconds) overflowed and was read as no `Retry-After` at all, so the call was re-sent about 2 seconds later; every `Retry-After` is now capped at the 2-hour bound the gate uses, before it is converted (BH1).
- **With `tracker.outbox: false`, a comment posted from the dashboard was queued and never delivered.** The API answered `202 queued`, but with the outbox switched off nothing drains it. The comment is now posted directly (`200`). Entries left from an earlier outbox-on run stay visible and can be retried or discarded. (CORE-120)
- **If the outbox could not store an input-required question, tracker replies never resumed the agent.** The failure (for example a read-only `.itervox/`) was only logged, and the question's key, which a reply must match, pointed at a comment that would never exist. The question is now posted directly without a key, and replies are matched to that comment. If that post fails too, the key is kept, so an answer to an earlier question on the same issue can never resume the agent by mistake, and a warning says to answer from the dashboard or dismiss. (CORE-121) If that direct post succeeded while the daemon was shutting down or reloading, the result could be lost without a log line and the saved question kept a key no comment carries, so after the restart no tracker reply could match it; the saved question is now updated to the posted comment before shutdown completes, and the comment id is logged (BH5).
- **A comment queued by a build before idempotency keys could be posted twice after a crash, on Linear too.** On load, such an entry got a new random key each time the daemon started, so a crash just after a successful post led to a second post under a different key. The key is now derived from the entry's id and saved at load, so it is the same on every start. (CORE-122)
- **An oversized input-required question could block the issue's tracker writes.** On the explicit input-required path the agent's text went into the question comment without a size limit. A comment the tracker rejects as too long stays at the head of the issue's outbox queue, where it holds up the reply and the completion state change. The comment now carries at most 8 KiB (the end of the text); the dashboard shows the full text. A question the tracker keeps rejecting for another reason (a locked or deleted issue) is still retried rather than dropped, since the same errors can come from a fixable token or permission problem. The daemon now logs one warning once it is degraded, instead of a debug line on every tick. (CORE-123)
- **On Linear, a question in an issue with more than 50 comments could be missed.** The issue detail read one page of 50 comments, and which end of the thread that page held was never established. A question outside that page was never found, so a reply in Linear never resumed the agent. The detail now reads the thread page by page (up to 500 comments) and sorts it oldest-first whatever order Linear returns. For threads longer than that, the page order still decides which comments are read. (CORE-124)
- **`itervox stop` could kill an unrelated process that had reused a dead daemon's pid.** After a daemon was SIGKILLed or crashed, its `.itervox/daemon.pid` stayed behind, and `stop` signalled the recorded pid as long as it was alive and the file named the right `WORKFLOW.md` — SIGTERM and then, after the grace period, SIGKILL — so an editor or shell that inherited the pid was killed. `stop` now uses the daemon's pid lock (CORE-039): if the lock is free the record is stale, and it is removed without signalling anything; a pid is signalled only while another process holds the lock, and the SIGKILL escalation re-checks that the lock is still held by the same record. The directory-scan fallback follows the same rule. Pre-v0.2.1 records and scan hits without a held lock need `--legacy`. See Upgrade note 15. (CORE-163)
- **An agent that asked for input through its CLI was treated as a failed run.** Claude and Codex report an input request on an error result event (a Claude `result` with `is_error`, a Codex `turn.failed`), and every failed turn was classified before the input-required check. So the run was retried or moved to `tracker.failed_state` instead of waiting for a reply; only the `<!-- itervox:needs-input -->` sentinel reached the input-required queue. Such a turn now goes to the input-required queue, keeps its handoff file un-renamed, and posts its question. The question is the agent's own last message, or else the CLI's error message; the agent's stderr, which can carry exported secrets, is never used. Every input-required question (sentinel and fallback detector too) is also passed through the log redactor before it becomes a tracker comment, the dashboard entry or an automation prompt. A genuine error result is still a failure. An error only counts as an input request when it says the agent is waiting for a person's answer ("human turn", "needs your input", "waiting for user input"). Wording such as "approval", "interactive" or "confirmation required" does not count, because Claude and Codex use it for configuration errors: a non-interactive session, `approval_policy` never, or an unapproved MCP server. Those are still retried. (CORE-164, CORE-166)
- **A successful agent run could stop and wait for input only because its summary said "approval" or used other everyday wording.** The fallback input-required detector gave the full score to bare words, so "Got approval and merged the PR.", "the handler will now respond with a 404", "ran the suite before proceeding", "documented which one of the two paths runs first" or "changed the field type 'int'" halted a finished run. Only direct asks ("please confirm", "I need approval", "need your permission", "should I …", "would you like me to …") now count on their own. Bare words need a second signal, such as a closing question or a list of replies. Reply instructions ("Reply with …", `Type "x"`, "Pick one") count on their own only at the start of a sentence. (CORE-159)
- **Log lines for unfamiliar tools showed a different description each time.** For a tool without a dedicated summary (for example an MCP tool), the description was the first string field found in a Go map, whose order is random, so the same call could be summarised by a different field on each line. The first non-empty string field in sorted key order is now used. (CORE-137)
- **Cancelling a turn on an SSH worker now stops the remote agent instead of leaving it running.** A cancelled or timed-out turn, or a daemon shutdown, killed only the local `ssh` client. ssh runs without a PTY (`-T`), so nothing sent the remote side a hangup, and a remote `claude`/`codex` that was thinking rather than writing kept running on the worker, along with everything it had started, until it finished by itself. The daemon now keeps the connection's stdin open for the whole turn, and the fixed remote wrapper watches it: when the client goes away, sshd closes the session, the wrapper sees end-of-file, sends `SIGTERM` to the agent's own process group (the agent and its descendants) and `SIGKILL` 2 seconds later. A turn that ends normally is unaffected: same output, same exit status (including Codex's `pipefail`/`tee` status), and the agent's stdin carries nothing from the ssh channel (since CORE-156 it holds only the prompt). The script on stdin now ends with a NUL instead of end-of-file. Workers need `bash` 3.2+, `sh`, `cat`, `printf`, `wc` and `sleep` (`uname` is no longer needed since CORE-156); any SSH server works, OpenSSH or Dropbear. A login profile that reads stdin to end-of-file now blocks the turn until it is cancelled, where it used to fail at once with "arrived truncated"; one that reads a line or a fixed number of bytes still fails that way. Processes that leave the agent's process group (for example with `setsid`) are not reached, as for local turns. If the network drops without the client dying, the agent is stopped only when sshd's `ClientAliveInterval` or TCP keepalive notices. The wrapper signals only the process group it creates for the agent, never its own group, so on Dropbear, which runs every session of a connection in one process group, cancelling one turn no longer kills the server connection and every other agent sharing it (for example through `ControlMaster`); a login profile's `readonly TMOUT` (CIS hardening) no longer stops a running turn after TMOUT seconds; and a normally finished turn never signals anything, including a background job the login profile started or a process the agent left running. The worker-side watcher also no longer depends on the login profile's shell options or variables. A profile that turns on `set -e`, `set -u` or `pipefail` no longer stops a cancel from killing the agent; the agent's script still runs under those options, as before. A profile that unsets `SECONDS`, and wall-clock steps, no longer cause a live turn to be killed after a few seconds on bash 3.2. The script also really keeps a profile's `set -e` now; an earlier version of this fix dropped it. A signal the agent or one of its tools sends to its own process group (`kill 0`, `kill -USR1 0`: HUP, USR1, USR2, ALRM, PIPE or TERM) no longer disables the cancel, and it no longer ends a turn whose agent ignores that signal (CORE-155).
- **Long prompts no longer stop an agent from starting.** The prompt (SOUL, INSTRUCTIONS, the issue template and every prior agent handoff) was passed to `claude`/`codex` as one command-line argument. Linux allows at most 131,072 bytes in one argument, so on a Linux SSH worker any prompt of 128 KiB or more was refused with exit 98 ("MAX_ARG_STRLEN"), and a local turn failed with "argument list too long" (on macOS once the prompt and environment passed about 1 MiB). Pipelines with long handoff chains hit this. The prompt now reaches the agent CLI on its standard input, byte for byte, and the CLI sees end-of-file right after it: Claude runs as `claude ... -p` with no prompt argument, Codex as `codex exec ... -` (and `codex exec resume <id> -`). Nothing prompt-sized is a command-line argument any more, so the exit-98 refusal is gone. Over SSH the prompt still travels inside the script on the connection's stdin; the worker's bash hands it to the agent through a process substitution (`bash` 3.2+ with `/dev/fd` or a writable `TMPDIR`; `uname` is no longer needed). Locally it goes through an unlinked, owner-only temporary file, passed as the agent's stdin or, under the login shell, as file descriptor 3 so that a login profile that reads stdin cannot consume it. Cancel behaviour is unchanged. Limits: Claude Code itself refuses piped input over 10 MB, and over SSH a 1 MiB prompt of quote-heavy text adds about 3 s to the start of a turn, because the worker reads the script one byte at a time (CORE-156). Follow-ups: a prompt over Claude Code's piped-input limit (10,485,760 characters as the CLI counts them, measured in Claude Code 2.1.283) now fails the run before the CLI starts, with an error naming the limit, instead of failing inside the CLI; nothing is truncated. Codex has no client-side limit (its context window is enforced by the server), so no check applies there. Over SSH, a login profile that leaves `set -a` (allexport) on exported the prompt: from 128 KiB on Linux (1 MiB on macOS) the worker failed with "Argument list too long" and exit 97, wrongly blaming a profile that reads stdin, and smaller prompts leaked into the environment of the agent and every tool it ran. The remote wrapper now turns allexport off before it reads the script and does not turn it back on; variables the profile exported stay exported.
- **A per-issue backend pin could run `claude` under the Codex runner (or the reverse).** Pinning an issue to `codex` while its profile's command was `claude …` produced `@@itervox-backend=codex claude …`; the Codex runner then executed `claude … exec --json`. ### Security

- **Removing `agent.ssh_strict_host_checking` from `WORKFLOW.md` kept the old mode until restart.** On a reload without the key the daemon kept whatever default an earlier version of the file set — including `no`, which accepts any host key — instead of returning to the safe `accept-new` default. Per-host overrides were already cleared on reload; the default is now reset the same way. (CORE-140)
- **An invalid SSH `StrictHostKeyChecking` setting silently fell back to trust-on-first-use.** A mistyped `agent.ssh_strict_host_checking` (for example `strict`) or per-host value (for example `Yes`) was ignored with no log, so an operator who meant to reject unknown host keys ran with `accept-new`, which accepts any host on first contact. Config validation now rejects the value (see upgrade note 11), and the runtime setters log a warning for any invalid value that still reaches them (CORE-140).
- **SSH-hosted agent commands could leak the remote environment (including secrets) into the agent stream, run in the wrong directory, and were injectable through issue text on some login shells (C1, CORE-139, CORE-154, CORE-155, CORE-156).** OpenSSH joins ssh's remote-command arguments into one string that the remote login shell parses again; splitting the wrapper into separate `ssh` arguments (`bash`, `-lc`, the script) made the login shell run only the first word of the intended script and the rest as its own commands — printing exported remote variables (API keys included) to the agent's stdout, starting the agent in the remote home directory instead of the configured workspace, silently dropping the `pipefail` guard that catches a crashed remote Codex run (CORE-139), and never running the sub-log fetch script at all. Quoting the whole script as a single `bash -lc '<script>'` argument fixed the argument-splitting bug, but was still injectable: a login shell of csh or tcsh treats a bare newline inside single quotes as the end of the string, so a prompt built from issue text (which can be a public GitHub issue) could run its own later lines as commands on the worker.

  The current wrapper (`internal/agent/ssh.go`) closes both holes. The one ssh argument is a small, fixed script built only from constants and integers — it contains none of the characters (`'`, `\`, `!`, newline) whose meaning differs across login shells, so it runs byte-identical whichever of sh, bash, zsh, dash, ksh, csh or tcsh is the worker's login shell (fish is safe by construction, not verified). The real script and prompt never appear in that argument at all: they travel over ssh's own stdin, NUL-terminated, with an exact byte-count check that refuses to run ("remote command arrived truncated") if a login profile consumes part of the payload first, rather than silently executing a fragment. `set +vx` runs before a single script byte is read, so a profile's own `set -x`/`set -v` can no longer trace secrets from the script into stderr (M1-B2 round 3, m1). The prompt itself no longer touches argv at all (CORE-156): it reaches the agent CLI over its own stdin via a process substitution, which also removes the Linux `MAX_ARG_STRLEN` (128 KiB) ceiling on prompt size. A background watcher inside the job's own process group (`cat` blocked reading the ssh channel) sends `SIGTERM` then `SIGKILL` to the agent's process group the instant the local client disconnects (CORE-155), without touching sshd or sibling sessions — which matters on Dropbear, where every session on a connection shares one process group. No PTY is ever requested (`ssh -T`), so nothing can corrupt the payload through terminal line-discipline translation. Workers need only `bash` 3.2+, `sh`, `cat`, `printf`, `wc` and `sleep`.

  If you ran SSH workers with a debug-level daemon log before this landed, check those logs for leaked remote environment variables and rotate any secrets they contain.
- **The bearer-token dashboard URL was written to stderr even when stderr was a log sink.** Under systemd, a container, or any redirected stderr, the `?token=` URL landed in journald / CloudWatch / Cloud Logging / Log Analytics, so anyone who could read those logs **and** reach the bind address (or its tunnel/proxy) held a valid bearer token. The tokenised URL is now printed only when stderr is a terminal, or when `ITERVOX_PRINT_TOKEN=1` forces it; `--no-print-token` suppresses it in every mode. Otherwise the startup line carries the token-free URL and a `sha256:` fingerprint, plus — for an auto-generated token — the path of `<logs-dir>/api-token` (mode 0600), which holds the token. The token never reaches the rotating log file (text or JSON). See Upgrade note 10. (CORE-012)
- **A remote login profile that enabled shell tracing copied the remote script, including secrets, into the failure text.** If the worker's login profile (or `BASH_ENV`) ran `set -x` or `set -v`, bash traced the stdin script up to five times to stderr, and stderr becomes the turn's failure text, which reaches the daemon log, the per-issue log, the dashboard and the input-required context. The script holds `agent.command` (which can carry `VAR=secret` assignments) and the prompt. The wrapper now starts with `set +vx` before it reads a single script byte, so only the login shell's own trace of the fixed, secret-free wrapper line can appear (M1-B2 round 3, m1).
- **In `server.allow_unauthenticated` mode, any web page could change daemon state.** With no API token there is no bearer check, so a page the operator happened to visit could POST to a loopback or LAN daemon: queue a refresh, terminate or cancel issues, post a tracker comment as the operator (which can fire `tracker_comment_added` automations), or rewrite `WORKFLOW.md` through the settings routes. In that mode, state-changing API requests (POST, PUT, PATCH, DELETE) are now refused with 403 `cross_origin_forbidden` when the browser marks them cross-site or same-site (`Sec-Fetch-Site`), or when their `Origin` host and port do not match the request's `Host` (the scheme is not compared, so a TLS-terminating proxy keeps working; `Origin: null` never matches). Requests with neither header, such as curl, scripts and the TUI, are unaffected, as are GET requests and the SSE streams. With an API token (the default) nothing changes, because a browser never attaches the bearer token cross-site. See Upgrade note 13. (CORE-041)
- **`POST /api/v1/issues/{id}/backend` stored any string as the issue's backend.** The value is spliced into the agent command as a backend hint that is split at the first whitespace, so a value such as `claude printf AUDIT #` put a command into the runner's shell. Only `claude`, `codex` and `""` (clear the override) are now accepted, compared exactly (no trimming or case folding); anything else is a 400 `bad_request` with `field: "backend"` and never reaches the orchestrator. The same caller could already set an arbitrary profile command, so this closed an unvalidated input rather than a privilege escalation, but it also shrank what a forged request could do in unauthenticated mode. (CORE-040)
- **DNS rebinding gave any web page full control of a daemon running with `server.allow_unauthenticated: true`, including running commands.** A page on a hostname the attacker controls can re-point that name at `127.0.0.1` and then talk to the daemon same-origin, which the CORE-041 cross-origin guard correctly allows. Nothing checked the `Host` header, so such a page could `PUT /api/v1/settings/profiles/{name}` with an arbitrary agent `command` (run on the next dispatch), rewrite settings, and read `/api/v1/state`, the logs and the SSE stream. In unauthenticated mode every route (API, SSE, dashboard and static files) now requires a `Host` that is `localhost`, an IP literal (a rebinding attack always uses a DNS name), the configured `server.host`, or a name in the new `server.allowed_hosts` list; others get 403 `host_not_allowed`. `GET /api/v1/health` stays exempt because it returns a constant. Token mode is unchanged: a rebound page never holds the bearer token. See Upgrade note 14. (CORE-162) Follow-up: a `server.allowed_hosts` entry the check could never match was accepted without a word, so the proxy or tunnel it was meant for still got 403. Entries are now lower-cased with any `:port` and trailing dot dropped, and a Unicode name is converted to the punycode (`xn--`) form browsers send; a URL (`https://proxy.example`), a path, `user@`, a wildcard (`*.ts.net`; not supported, list each full name) or an invalid name now stops the config from loading, with an error naming the entry (BH2).
- **Any local user could keep the daemon from starting by locking its pid lock.** `.itervox/runtime/daemon.pid.lock` was created 0644 in a 0755 directory, and `flock` works on a read-only descriptor, so any user on the machine could hold the lock and make every start fail with "another daemon already running". The lock is now created 0600 and opened with `O_NOFOLLOW` (a symlink planted at its path is refused instead of followed), and `.itervox/runtime/` is created 0700. A directory or lock file left 0755/0644 by an older version is tightened on the next start when the daemon's user owns it; otherwise a warning is logged and startup continues. The pid record was already 0600. (M1-B6 round 2)
- **Any local user, or a suspended `itervox init --update`, could hang every settings save.** The `WORKFLOW.md` edit lock added by CORE-149 (`.WORKFLOW.md.lock`) was created 0644 and waited for the lock with no time limit, and `flock` works on a read-only descriptor. Another user on the machine holding it, or an `itervox init --update` stopped with Ctrl-Z mid-edit, blocked every dashboard and TUI settings save forever, and each blocked save held the daemon's in-process lock too. The lock file is now created 0600, opened with `O_NOFOLLOW` (a planted symlink is refused), and tightened when an older version left it 0644; a save that cannot get the lock within 10 seconds fails with an error naming the lock file and the likely cause, and nothing is written. (BH4, follow-up to CORE-149)
- **Secrets in an agent's stderr reached the daemon log, the dashboard and tracker comments.** A failed turn's text includes the agent's stderr, which can echo exported keys; it went to the "turn failed" log line, the retry row on the dashboard, and the comment posted when retries run out. The log redactor knew only Anthropic, Linear and GitHub `ghp_` token shapes, and it never looked at error-typed log attributes at all, so that line was not redacted even for those. The failure text is now redacted where it is built, and again in the worker, before any of those uses; error and `String()`-typed log attributes are redacted like strings; and the redactor now also masks OpenAI keys (`sk-proj-`, `sk-svcacct-`, `sk-admin-`, legacy `sk-` + 40 characters), every GitHub token prefix (`gho_`, `ghu_`, `ghs_`, `ghr_`), Slack tokens, AWS access key ids, JWTs, PEM private keys, URL passwords, the value of any `UPPER_CASE_NAME=value` whose name contains `SECRET`, `TOKEN`, `PASSWORD`, `API_KEY`, `PRIVATE_KEY`, `ACCESS_KEY` or `CREDENTIAL`, and any 32+ character run that mixes upper case, lower case and digits with high character entropy. Git SHAs, UUIDs, paths and identifiers are left readable. Not caught: a random secret shorter than 32 characters that has no known prefix and is not assigned to a secret-named variable. If you ran agents that print credentials, check older daemon logs and rotate what they contain (CORE-167, CORE-104). Follow-up (M2-close): an independent check still found shapes reaching the retry row, HEARTBEAT, the issue log, the max-retries tracker comment and the daemon log: `Authorization: Basic` credentials, lower- and mixed-case names (`password=`, `passwd:`, `secret=`, `api_key=`, `"apiKey":`, `x-api-key:`, `aws_secret_access_key =`), URLs with an empty user (`https://:TOKEN@host`), GitLab `glpat-` tokens, Slack `xapp-` tokens, a random token inside a path (`/hooks/<token>`), and random tokens with no digit. All are masked now. It also masked too much: vendor request ids (`req_…`, `msg_…`), SRI hashes (`sha512-…`) and branch names or paths with mixed case and digits are kept readable again. The max-retries comment is additionally redacted where it is written.
- **The dotenv startup line now also names `OPENAI_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` when `.env` supplied them** (names only, never values) (CORE-104).

### Known limitations

- **GitHub only:** if the daemon is killed after GitHub accepts a comment but before the attempt is recorded, the comment can be posted again after restart. Linear is not affected — a re-sent comment with the same id is rejected and then found by lookup.
- A tracker's published reset is treated as a hard window: no requests are sent to that tracker until it passes.
- With `tracker.outbox: false`, input-required questions and replies are posted with a single direct attempt (not queued), and replies are matched to the most recent question by position.
- A tracker comment is matched to an in-flight question by its creation time, so it must carry one. Both Linear and GitHub report it; a comment without a timestamp waits until the question comment appears and the reply is below it.

## [0.2.0] — 2026-07-06

### Migration from v0.1.x

> **Schema 2 is mandatory.** `WORKFLOW.md` files now require an `itervox_schema_version: 2` marker at the top, and inline `agent.profiles.<name>.prompt` is no longer accepted. On startup the daemon hard-fails with a `MissingWorkflowSchemaMessage` pointer when either condition is unmet. To migrate an existing v0.1.x project:
>
> ```bash
> itervox init --update --workflow WORKFLOW.md
> ```
>
> The migrator writes a `WORKFLOW.md.bak` next to your workflow, extracts each profile's inline `prompt:` block into `.itervox/agents/<name>/INSTRUCTIONS.md`, generates a compact `.itervox/agents/<name>/SOUL.md` identity file, and ensures the git policy via a nested `.itervox/.gitignore` (always written; also self-healed on every daemon startup) plus root-`.gitignore` carve-outs when a root `.gitignore` broadly ignores `.itervox/` — so `.itervox/agents/**` and `.itervox/handoff/**` can be committed while runtime state stays ignored. Review the migrated `WORKFLOW.md` and the new agent files, then delete `WORKFLOW.md.bak`. See [Agent Profiles guide](https://itervox.dev/guides/agent-profiles/) for the file-backed profile reference.
>
> **If you set `workspace.auto_clear: true` on a v0.1.x project,** the migrator will print a one-line warning to remind you that v0.2.0 changes the semantics from "clear after every successful run" to "clear only when the issue reaches a terminal tracker state." For features that succeed on first attempt, behavior is unchanged. See the **Changed (breaking)** section below for the full rationale.

### Removed (breaking)

- **Inline `agent.profiles.<name>.prompt` is rejected by schema 2.** Each profile must now reference SOUL/INSTRUCTIONS files via `soul_file` and `instructions_file` (typically `.itervox/agents/<name>/SOUL.md` and `INSTRUCTIONS.md`). Use `itervox init --update --workflow WORKFLOW.md` to migrate; see the Migration section above.
- **`agent.agent_mode`** is gone. The previous values were `""` (solo), `"subagents"`, `"teams"`. Behavior reasoning:
  - `""` and `"subagents"` were aliases at runtime — the daemon never actually gated subagent dispatch.
  - `"teams"` injected a "your peer agents are X, Y, Z" roster into worker context; that injection now happens **unconditionally** when more than one profile exists.
  - Profile content (now `INSTRUCTIONS.md`) always injects when a profile is selected. Previously the legacy inline `prompt:` was suppressed unless `agent_mode` was non-empty — silent suppression that operators rarely intended.

  **Migration:** delete the `agent.agent_mode` field from your `WORKFLOW.md`. The daemon now hard-fails at startup with a clear pointer to this entry if the field is present (typo guard). The legacy alias `agent.enable_agent_teams` is similarly rejected.
- The **`POST /api/v1/settings/agent-mode`** HTTP endpoint and the **"Agent Runtime"** Settings card are removed. The `inline_input` toggle (which used to live in that card) now lives in Settings → General and still persists to `WORKFLOW.md::agent.inline_input`.
- The TUI status row no longer displays a `◈ SUB-AGENTS` / `◈ TEAMS` badge.

### Changed (breaking)

- **`workspace.auto_clear: true` semantics changed.** Previously the workspace was removed after **every** successful worker run (mid-pipeline state transitions included). It now clears **only when the issue reaches a terminal tracker state** — either `tracker.completion_state` after a successful run, or `tracker.failed_state` after retries are exhausted. The field name and type are unchanged.

  **Why:** the per-success clear pattern broke the new file-backed agent handoff convention (see Added), which expects `.itervox/handoff/` files to accumulate across multiple workers running on the same branch for one issue. The new semantics preserve the workspace across retries and pipeline mid-states and only clean up once the issue is definitively done.

  **Who is affected:** users relying on per-run disk-space hygiene for flaky issues that retry many times will see workspaces persist across retries until the issue reaches `failed_state`. For features that succeed on first try, behavior is unchanged. `itervox init --update --workflow WORKFLOW.md` now prints a one-line notice when it finds `workspace.auto_clear: true` so the semantic shift is not silent.

  **Workaround for old behavior:** none in-tree. Run an external cleanup (e.g. `find <workspace_root> -mtime +1 -delete`) outside the daemon if eager clearing is required.

- **`workspace.auto_clear` + `agent.auto_review` no longer conflict.** Under the legacy per-success clear semantics the two settings raced — the clear removed the workspace before the reviewer could read it. Validation rejected the combination at config-load and at runtime PUT/PATCH. With the new terminal-state-only semantics the clear is deferred until after the reviewer also completes, so the two now safely coexist. `ValidateAutoClearAutoReview` is retained as a no-op for callers that branch on `ErrAutoClearAutoReviewConflict`; new code should not call it. Operators who relied on the validation error to catch accidental over-configuration should note that both flags will now silently be accepted.

### Added

- **`[SILENT]` no-op convention for tracker comment delivery.** When an agent run's final output begins with `[SILENT]` (case-sensitive, leading whitespace ignored), the session summary is not posted as a tracker or PR comment. The run remains fully visible in the dashboard's per-issue logs — only the tracker notification is suppressed. Designed for recurring automations (hourly scans, nightly checks) whose common case is "nothing to report"; instruct the agent to reply `[SILENT] <short reason>` on the no-findings path. A `[SILENT]` occurring mid-message does not suppress. See the [Automations guide](https://itervox.dev/guides/automations/) for a cron example.
- **`itervox_schema_version: 2`** is now required at the top of every `WORKFLOW.md`. The daemon validates this marker at startup via `MissingWorkflowSchemaMessage` and refuses to run when it is absent. Existing v0.1.x workflows are migrated by `itervox init --update --workflow WORKFLOW.md` (see the Migration section above).
- **File-backed agent profiles.** Profile identity and operating instructions now live in `.itervox/agents/<name>/SOUL.md` (compact who-you-are file) and `.itervox/agents/<name>/INSTRUCTIONS.md` (full behavioural rules), referenced from `WORKFLOW.md` via `agent.profiles.<name>.soul_file` and `instructions_file`. `.itervox/agents/**` is committable; the root `.gitignore` is patched by `itervox init` and `itervox init --update` to allow it while keeping `.itervox/.env`, `.itervox/HEARTBEAT.md`, logs, and runtime queue files ignored.
- **File-backed agent handoff (`.itervox/handoff/`).** Each worker run can leave a Markdown deliverable at `.itervox/handoff/<ISO8601-timestamp>_<profile-name>.md` on the issue's worktree branch. On the next worker dispatch for the same issue, the orchestrator reads every `.md` file in that directory in chronological order (lexicographic = chronological because the prefix is ISO8601), concatenates them with separators, applies a token budget (default 30 KB; oldest dropped first with a `[earlier handoffs truncated]` marker), and inlines the result into the agent's prompt under a `## Prior Agent Handoffs` heading.

Profile INSTRUCTIONS.md scaffolds now include a "Handoff Protocol" section instructing the agent to read the prerendered prior-handoffs block and write its own deliverable to `run.handoff_path` before exiting. Files are gitignore-carved-out via `!.itervox/handoff/**` (same pattern as `!.itervox/agents/**`) so the pipeline trail commits cleanly into PRs. ### Multi-daemon coexistence and operator diagnostics (v0.2.0 closing-pass)

- **Default `server.port` is now `0` (OS picks a free port).** When
  `server.port` is omitted from `WORKFLOW.md`, the daemon binds an
  OS-assigned free port instead of skipping the HTTP server. Two itervox
  daemons in two different repos now coexist out of the box. The actual
  bound URL is written to `.itervox/dashboard_url` and surfaced in
  `HEARTBEAT.md`, the startup banner, and `itervox doctor`. **Operators
  who explicitly pinned a port in WORKFLOW.md are unaffected**; an
  explicit port still binds strictly.
- **`EADDRINUSE` is now a fatal startup error.** When `server.port` is
  explicitly set to a port already in use, the daemon prints a structured
  diagnostic naming the holding process (via `lsof`), writes
  `.itervox/STARTUP_ERROR.md`, and exits non-zero. The previous behaviour
  silently auto-shifted to the next free port, mismatching the Vite dev
  proxy / `dashboard_url` / `HEARTBEAT.md` contract. The hint in the error
  recommends `server.port: 0` for "two daemons in parallel" workflows.
- **`itervox init --update --server-port <n>` migration flag.** Rewrites
  `server.port` in an existing `WORKFLOW.md` (back-compat: omit the flag
  to leave the field alone). `0` is the recommended value for new
  multi-daemon setups; explicit ports still work for single-daemon
  setups that pin a known URL.
- **`itervox init` scaffolds `server.port: 0`** by default in fresh
  `WORKFLOW.md` files. Operators who want a fixed port edit the value
  after init.
- **Pidfile + `HEARTBEAT.md` cleanup on shutdown.** `.itervox/daemon.pid`,
  `.itervox/HEARTBEAT.md`, and `.itervox/dashboard_url` are removed
  together on SIGINT/SIGTERM so a clean exit leaves no stale liveness
  state. Doctor's HEARTBEAT-stale check catches the crashed-without-
  cleanup case.
- **Refuse-to-start when a previous daemon is alive.** Startup reads the
  pidfile; if the recorded PID is still alive, the daemon refuses to
  start with `itervox: another daemon already running for this WORKFLOW.md
  (pid=<n>, recorded_workflow=<path>)`. Stale pidfiles (PID dead) are
  silently overwritten with a slog notice. Prevents the "two daemons
  fight over `.itervox/automation_queue.json`" symptom triad.
- **`.itervox/dashboard_url` file + Vite auto-discovery.** Daemon writes
  the actual bound URL atomically after the listener binds. `vite.config.ts`
  walks up from `process.cwd()` looking for the file and uses it as the
  proxy target. `ITERVOX_PROXY_TARGET` env var overrides for CI.
  Fallback to `http://127.0.0.1:8090` keeps fresh-checkout `pnpm dev`
  working.
- **`itervox doctor` mitigation checks.** New `DoctorReport` fields:
  - `PortInUseWarning`: configured port held by a non-itervox process.
  - `HeartbeatStaleWarning`: `HEARTBEAT.md` exists but the recorded
    daemon PID is dead.
  - `DashboardURL` + `DashboardURLReachable`: probe `<dashboard_url>/api/v1/health`.
  - `ItervoxBinEnv`: read from the env so the drift report can
    downgrade severity when the operator has pinned `ITERVOX_BIN`.
  - `--clear-startup-error` flag for the "I already fixed it" workflow.
  - Binary-drift severity heuristic: only the "dev vs stable" case
    (one binary reports `version=dev`, the other a release tag) is
    ERROR; two stable installs with different SHAs render as `info:`.
- **Restart loop bails on fatal startup errors.** A new
  `fatalStartupError` sentinel marks "operator must intervene" failures
  (e.g. configured port in use). The outer `run()` restart loop exits
  via `fatalExit(1)` instead of retrying every second.

### Security

- Bearer token is no longer written to the rotating log file at `~/.itervox/logs/`. The tokenized dashboard URL now goes through a stderr-only logger that bypasses the file sink.
- `loadDotEnv` now emits a single structured Info log naming sensitive keys configured from `.itervox/.env` (never their values), giving operators visibility into which secrets are file-sourced.
- **SSH host-key checking now defaults to `accept-new` (TOFU)** instead of `no` (T-32). On first contact with a new SSH worker host the daemon pins the key in `known_hosts`; subsequent connections that present a different key are rejected with a clear `ssh: host key verification failed` instead of being silently MITM'd. Per-host overrides are configurable via `agent.ssh_strict_host_checking` (default for all hosts) and `agent.ssh_strict_host_by_host` (`{host: mode}` map) in `WORKFLOW.md`. Modes: `yes`, `no`, `ask`, `accept-new`, `off`. Closes F-NEW-F.
- **Defense-in-depth secret redaction at the log sink** (T-29). A new `internal/logging.RedactingHandler` middleware wrapping the file fanout scrubs Anthropic / Linear / GitHub PAT / `Authorization: Bearer …` patterns from any record that reaches `~/.itervox/logs/`. Pairs with the new `logging.Secret` `slog.LogValuer` for the structured-attr path. Stderr-only emits (the dashboard-token URL) are deliberately left unwrapped so the operator can still copy the URL once on startup.

### Conformance hardening — adversarial-audit final pass (2026-07-05/06)

Before tagging, an adversarial audit verified Itervox against the [Orchestrated Coding spec](https://github.com/vnovick/orchestrated-coding) it claims L3 conformance with (one auditor per subsystem, refute-first verification of every finding, per-fix regression tests run under `-race`). The user-facing changes:

#### Changed (behavior)

- **`merge_pr` refuses unarmed gates.** On a repository with zero required checks, `gh pr checks --required` passes vacuously — "a gate that can never fail is not a gate" (spec F3). The merge action now refuses with reason `unarmed_gate` and an actionable message. Opt out per project via the new `agent.allow_unchecked_merge: true` (default `false`), which merges with a loud warning instead. Check-refusal details are no longer empty: gh's stderr diagnostic is captured into the `checks_failed:`/`unarmed_gate:` reason.
- **`merge_pr` no longer passes `--delete-branch`.** gh's post-merge *local* branch delete fails when the PR branch is checked out in an Itervox worktree, turning a successful merge into an error (dedup unrecorded, `pr_merged` automations lost). The merge now runs without the flag; the remote branch is deleted best-effort afterwards, and local branches are cleaned by workspace auto-clear.
- **GitHub blocker lookups are strictly fail-safe (spec D4).** Any blocker fetch error — including 404, which GitHub also returns for permission loss and transferred issues — now leaves the dependency state *unknown*, keeping dependents blocked. Previously a 404 fabricated a `closed` state and could falsely unblock work. A genuinely deleted blocker now blocks its dependents until the reference is removed from the issue body; the Deps tab shows the row as `unknown`.
- **"Update the shared state" is now part of done (spec F2).** A worker that exits successfully without writing its handoff gets one **synthesized** from the session summary (explicitly marked as synthesized); if synthesis fails, the unit fails. Handoffs (agent-authored and synthesized) are committed on the issue branch with a pathspec-scoped `chore(itervox): record agent handoff` commit before the PR push, so the pipeline trail is durable — expect this commit to appear on issue branches.
- **Pause windows park automations instead of deleting them (spec D7).** While `agent.pause_dispatch_when_any_in_state` is active, triggered automations are now durably queued with reason `paused_by_state` and released when the window ends. Previously the drain pass deleted queued entries — including restart-persisted ones — and one-shot events were lost. Parked entries consume queue capacity during long pauses (bounded by `max_automation_queue_length`).
- **`blockers_resolved` no longer re-fires on tracker outages.** A transient blocker-fetch outage used to arm the unblock latch and fire the automation again (dispatching real agents) once the outage cleared — even for issues that were never blocked. The latch now arms only on *known-blocked* status and disarms after each fire.

#### Added

- **`hooks.after_run_required`** (default `false`): makes the `after_run` hook a per-unit completion gate — a worker whose final hook exits non-zero fails the unit instead of completing it (spec F3: a unit is not done on the agent's self-assessment alone).
- **`agent.allow_unchecked_merge`** (default `false`): explicit opt-in to merge on repositories with zero required checks (see the `unarmed_gate` change above).
- **Dependency-audit ledger persists across restarts.** Blocked/unblocked state (and the unblock-transition watermark) is now stored alongside the durable automation queue (additive payload — existing state files load unchanged), so a blocker that closes while the daemon is down still fires `blockers_resolved` after restart. Previously such transitions were lost forever.
- **Nested `.itervox/.gitignore` covers all runtime files** (`daemon.pid`, `dashboard_url`, `STARTUP_ERROR.md`, `*.db` added), self-heals on every daemon startup, and `itervox doctor` warns when required lines are missing.
- **README "Spec conformance" section** stating the L3 claim with evidence links, per the spec's claiming procedure; the docs site gained a matching [Orchestrated Coding guide](https://itervox.dev/guides/orchestrated-coding/).

#### Fixed

- **Daemon crash:** a worker-exit event arriving after a reconcile kill path had already removed the issue from the running set panicked the event loop (nil dereference) and took down the whole daemon.
- **Duplicate workers / retry-ceiling reset:** the same stall-kill race could release the retry's claim, letting a fresh dispatch start at attempt 0 while the orphaned retry later overwrote the running entry — two agents on one worktree.
- **Failed runs' handoffs were never marked `.partial.md` for named profiles** (the exit event carried no profile name), and a failed default-profile run could rename a *predecessor's completed* handoff to partial. Partial-marking now uses the live run entry's profile and start time.
- **Dashboard-blanking enum gap:** the `pr_merged` automation trigger was missing from the dashboard's schema — one `pr_merged` rule in `WORKFLOW.md` made every snapshot fail validation and blanked the entire dashboard (silently, in production builds). Added, plus a Go↔TS parity test covering *all* automation trigger types.
- **Settings silently revoked `merge_pr`:** saving any profile from the Settings page stripped the `merge_pr` action (three drifted copies of the action list, all missing it) — including from the built-in merge-bot profile. The Settings UI now derives actions from the canonical schema and can grant `merge_pr`.
- **Data race on runtime tracker-state edits:** the board-fetch and TUI dispatch paths read `tracker.active_states`/`terminal_states`/`completion_state` without the lock that guards the settings-API writer (proven with the race detector); all runtime readers now use the guarded accessor.
- **`blockers_resolved` was structurally dead on GitHub for issues outside `active_states`:** the audit's refresh paths never populated blocker states, so watched issues could never transition to unblocked. All GitHub fetch paths now populate blocker states.
- **Snapshot aliasing:** the PR-dispatch dedup ledgers were the only state maps not deep-copied into snapshots; `PRMergedDispatched` was also never initialized nor janitor-pruned.
