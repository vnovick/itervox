An agent asked to fix a red build has two ways to make it green. It can fix
the code, or it can add `continue-on-error: true` to
`.github/workflows/ci.yml`. To git, both are an ordinary push to the issue
branch. Lanes tell them apart:

> An agent may change **what** CI checks, never **how** CI checks.

A fix, a new test, a new lint finding: that is what CI checks, and the push
goes through. A workflow file, the test runner's config, a coverage threshold:
that is how CI checks, and a human looks first.

Lanes are part of the [guardrails](/guides/guardrails/) and on by default. To
see them stop a real pipeline edit on your machine, run the
[pipeline-guard demo](/guides/pipeline-guard-demo/).

## The three lanes

Every file a push changes falls in one lane, the highest that matches. The
push takes the highest lane of any of its files.

| Lane | Files | What happens |
|---|---|---|
| `human` | `guardrails.lanes.human` (default below) | The push waits for your approval. `merge_pr` never merges the pull request. |
| `second_opinion` | `guardrails.lanes.second_opinion` (default: none) | The push goes through. `merge_pr` waits for an approving review from a reviewer on a different backend. |
| `auto` | everything else | Unchanged. |

The default human lane is short on purpose. It lists the files that decide
how a change is checked, not what it does:

```text
.github/**  .gitlab-ci.yml  .circleci/**
.itervox/**  !.itervox/handoff/**  WORKFLOW.md
CODEOWNERS  .github/CODEOWNERS
jest.config.*  vitest.config.*  pytest.ini  .coveragerc  codecov.yml
.golangci.yml  Makefile
```

`.itervox/handoff/` is left out because every run commits its handoff there.
`package.json`, `pyproject.toml` and `go.mod` are left out too: by path, their
test sections cannot be told apart from their dependency lists.

## Configure

```yaml
guardrails:
  lanes:
    human: [".github/**", ".gitlab-ci.yml", ".circleci/**", ".itervox/**", "!.itervox/handoff/**",
            "WORKFLOW.md", "CODEOWNERS", ".github/CODEOWNERS", "jest.config.*", "vitest.config.*",
            "pytest.ini", ".coveragerc", "codecov.yml", ".golangci.yml", "Makefile",
            "tox.ini", "scripts/ci/**"]       # your own
    second_opinion: ["internal/auth/**", "migrations/**"]
```

- Leave `human` out to keep the default.
- Setting `human` **replaces** the default, so copy it to keep it.
- `human: []` turns the human lane off.

Patterns are gitignore-style, over paths relative to the repository root:

- `*` and `?` match within one directory, `**` spans any number, `[…]` is a class;
- a pattern with no `/` matches that name at any depth (`Makefile` matches
  `services/api/Makefile`); one with a `/` is anchored at the root;
- a pattern that matches a directory matches everything under it;
- `!pattern` excludes what an earlier pattern of the same lane matched;
- matching is case-sensitive.

A pattern that names no path, or does not parse, is a startup error.

`guardrails.lanes` is read when the daemon loads its configuration, so a
change applies from the next reload. See the
[`guardrails` reference](/configuration/#guardrails).

## How a push is classified

The guardrails put a `pre-push` hook on every run Itervox starts. For each
ref the agent pushes, the hook lists the changed files through git
(`git diff --name-only -z --no-renames`) and looks each one up in the lanes.

- **A branch the remote already has:** the files that changed since the
  remote tip *and* that differ from the base branch. Merging the base branch
  in, as the guardrails tell agents to do, does not count as changing what the
  base changed.
- **A new branch:** the files that differ from its merge base with the base
  branch. The base is the pull request's base (the blocker's branch for a
  [stacked PR](/guides/stacked-prs/), else `workspace.base_branch`), then
  `agent.base_branch`, `origin/HEAD`, `origin/main` and `main`. The first one
  found wins.
- **Renames** count as a deletion plus an addition, so moving a workflow file
  away is caught too.
- **If the files cannot be listed,** the push is treated as human lane.

The lanes come from the policy the daemon writes for the run, built from the
daemon's own `WORKFLOW.md` and settings files. An edit to `WORKFLOW.md` or
`.itervox/` on the issue branch does not change the lanes of that run; it is
itself a human-lane change.

## A held push: Pipeline change

A human-lane push is held like an [approval command](/guides/guardrails/#approving-a-deploy).
It shows as **Pipeline change** on the dashboard (in the Needs-attention row
and the issue's Now panel), in the desktop app, on your phone and as a tracker
comment, with the files it changes (up to ten, then "and N more"):

> Pipeline change: the agent wants to push changes to `.github/workflows/ci.yml` (`git push origin refs/heads/itervox/eng-1`)

It also says **why**, concretely, with file and line:

> Why this needs a person:
> - `.github/workflows/ci.yml:10`: failure ignored in a CI workflow (continue-on-error / allow_failure: true) (`ci_continue_on_error`)
> - `.github/workflows/ci.yml` matched `.github/**` → human

Two kinds of reason, findings first:

- **Findings** on what the push adds: the same rules as
  [`itervox referee audit`](/guides/referee/) (a test skip, a deleted test, a
  focused `.only`, a lowered coverage threshold, `continue-on-error` /
  `allow_failure`, `|| true` in a workflow, `--no-verify`), with the line in
  the pushed version. A finding on a file outside the human lane (a
  `t.Skip` in a test the same push adds) is listed too.
- **Lane rules:** each held file and the pattern that put it in its lane.

Itervox computes these reasons itself, in the daemon, from the issue's
worktree and the commits the push names. The pre-push hook runs in the
agent's environment, so nothing it says about *why* is shown; when the
daemon cannot recompute the reasons (a commit it does not have), the
question lists the files with "reasons unavailable".

The list is bounded (twenty reasons kept, eight shown, then "and N more"),
each field is clipped, and secrets are redacted before anything leaves the
daemon. The text names the file, the line and the rule, never the added
line itself: that line is shown only to operator and admin tokens, in the
dashboard's approval card and the Lanes view. The same list is in the tracker comment, the dashboard card, the
[Slack message](/guides/slack/) (which links straight to the issue's
[Lanes view](/guides/now-and-changes/#lanes-view)) and
[`itervox watch`](/guides/terminal/) (the first three; `--json` has them all).
Findings are a reading aid, not the reason the push is held: the path decides
the lane.

- Reply `approve` to let **that** push through once. New commits ask again.
- Any other reply, or dismissing it, refuses the push. The agent is told your
  reply, so "fix the code, not the pipeline" reaches it.
- The agent cannot answer its own request.
- A tmux session started with **New session** has no approval channel: the
  push is refused and the agent is told to ask you.

While the push waits, the run's idle timeout is suspended, so the agent is not
failed for being quiet. `agent.turn_timeout_ms` still bounds the wait.

## Merging: merge_pr refuses

The daemon records each issue's pushes that reached the `human` or
`second_opinion` lane in `.itervox/push_lanes.json`. The record survives
restarts and is dropped when the issue is done. `merge_pr` checks it before
anything else:

| Recorded lane | `merge_pr` |
|---|---|
| `human` | refused with `lane_human`, even after you approved the push. Merging a pipeline change is a human's job. |
| `second_opinion` | refused with `lane_second_opinion` until a reviewer whose backend (`claude`, `codex`, …) did not write the change records an approving verdict after the last such push. |
| none | unchanged |

## Stack split: code and pipeline as two pull requests

When one run changes both ordinary code and human-lane files, the whole push
waits for a person, code included. With `guardrails.lanes.split: true`,
Itervox offers the run's changes as **two stacked pull requests** instead, so
the code waits for a person only when it depends on the pipeline change.

```yaml
guardrails:
  lanes:
    split: true        # default false
```

The split needs **[patches only](/guides/safety/#patches-only-the-daemon-pushes)**
(`push: daemon`), because only then does Itervox push the branch. An agent's
own pushes are never rewritten: with no profile on `push: daemon` the setting
does nothing, and the daemon logs a startup warning saying so (also when the
guardrails or the human lane are off). It also needs the profile's
[signed checks](/guides/signed-checks/) (`verify`), because the order is
decided by running them.

How it works, after the run's own checks passed and before anything is pushed:

1. The run's changed files (against the merge base with the pull request's
   target, which is what the single pull request and the run's checks are
   based on) are sorted with the same classifier the pre-push hook uses.
   Human-lane files go to the **pipeline** side; everything else, plus
   dependency lockfiles (`go.sum`, `package-lock.json`, `pnpm-lock.yaml`, …)
   and Itervox's handoff and evidence files, stays on the **code** side. A
   file is never divided. With no human-lane file, or nothing but human-lane
   files, nothing changes: one pull request as before.
2. Itervox builds a code-only and a pipeline-only commit on the base and
   runs the profile's `verify` checks on **the code alone**, in a temporary
   worktree. They are signed and stored like the run's own.
3. **The code passes alone:** the code goes first. `<branch>-code` is pushed
   and its pull request opened against the base right away; the pipeline
   change is the issue branch, stacked on it (its pull request targets
   `<branch>-code`), and its push waits for your approval as usual.
4. **The code fails alone:** the checks run on **the pipeline change
   alone**. If they pass, the pipeline goes first: `<branch>-pipeline`
   (after your approval) against the base, and the code stacked on it as the
   issue branch.
5. **Both fail alone:** no stack is offered. One combined pull request, as
   without the split, and the reason is recorded.

No branch in the stack is a broken middle: the lower one passed its own
checks, and the top has exactly the tree the run's checks passed on. The
pipeline pull request is stacked rather than opened independently against the
base, because base plus pipeline alone is a combination nobody tested.

The decision (the order, the files on each side, the branches, the pull
requests and the reason) is kept per issue in `.itervox/stack_splits.json`,
written to the run log, and fed as a `stack_split` event (`outcome` is
`code_first`, `pipeline_first` or `combined`; `count` is the number of
pipeline files). Both pull requests are linked on the issue.

Merge policy stays per pull request: `merge_pr` judges the lower, code-only
pull request of a code-first split by the code's own lane (`auto` merges;
`second_opinion` still needs its reviewer), and every other pull request of
the issue, the pipeline one included, by the issue's lane (`lane_human`).

Limits of this version:

- Only a branch's first push is split; a branch already on the remote, an
  issue [stacked on its blocker](/guides/stacked-prs/) and a run without
  `verify` get one pull request (the last two with the reason recorded).
- The checks on each half run in a fresh worktree of that commit: a check
  that needs ignored files the agent's worktree has (installed dependencies,
  build output) can fail there, and the split then falls back to one pull
  request.
- Later runs on the issue push to the issue branch, the top of the stack.

## Check your lanes

`itervox doctor` (and `itervox config show`) print a **Lanes** section:

```text
Lanes
  human: .github/**, WORKFLOW.md
  second_opinion: off
WARNING: implementer: verify check test runs `make test`, defined by Makefile, which the agent can change without a human; add it to guardrails.lanes.human
```

It shows the globs in effect (`(default)` when `human` is not set, `off` for
an empty list), warns when the human lane or the guardrails are off, and warns
when a [signed check](/guides/signed-checks/) runs a command whose definition
(`Makefile`, `package.json`, `tox.ini`, a script by relative path, …) is
outside the human lane. None of this changes the exit code.

## In CI: itervox referee lanes

The same rule works in CI, for any agent, with or without the daemon.
`itervox referee lanes` (or the standalone `referee` binary) sorts a pull
request's files into the same three lanes and exits with the result:

```bash
git fetch --no-tags origin main
itervox referee lanes --base origin/main [--head HEAD] [--policy .referee.yml] [--json]
```

| Exit | Lane |
|---|---|
| `0` | `auto` |
| `10` | `second_opinion` |
| `20` | `human` |
| `2` | an error (bad ref, malformed policy); never `0` |

Its policy is `.referee.yml`, **read from the base ref**
(`git show <base>:.referee.yml`), never from the branch being judged. A pull
request that edits the policy is judged by the old one, and the policy file is
always in the human lane. Without a policy file, the human lane is the same
default as above.

In GitHub Actions, use the referee Action with `mode: lanes`. Its `fail-on`
input (`human`, `second_opinion` or `never`) decides which lanes fail the
step, and its `lane` output names the result. If you run Itervox in CI with the
[GitHub Action](/guides/ci/), its [safer CI mode](/guides/ci/#safer-ci-mode)
also refuses a run whose `WORKFLOW.md`, `.itervox/settings.jsonc` or
`.itervox/agents/` differ from the base branch, so a branch cannot relax the
lanes it is judged by. See [referee](/guides/referee/) for the Action, the
policy format and an example workflow that requires a label on human-lane
pull requests.

## Known limits

:::caution[Guidance, not a sandbox]
Lanes see only pushes that go through the guardrail hook. An agent that runs
git by an absolute path, pushes through the GitHub or GitLab API with its own
token, or whose branch is edited on the web is not classified. `merge_pr`
decides on the recorded pushes; it does not re-read the pull request's file
list. **Branch protection and CODEOWNERS review on your remote** are the real
wall. Lanes keep honest agents honest; they are not a substitute.
:::

- Lanes are path patterns. A test-runner setting inside a file that is not in
  the human lane (`package.json`'s `jest` key, `pyproject.toml`'s
  `[tool.pytest]`, a `conftest.py` that skips tests, a test marked skip) is not
  seen. `itervox referee audit` reports common ones in CI; code review still
  matters.
- Runs on [SSH worker hosts](/configuration/#ssh-dispatch) are not guarded in
  this version.
- Sessions you start by hand are never touched by the shims and the pre-push
  hook. The [`itervox hook`](/guides/guardrails/#interactive-sessions-itervox-hook)
  PreToolUse hook asks before an edit of a human-lane file in your own Claude
  Code session (Codex: denies).
