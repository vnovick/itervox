Agents in CI can fix the build. Don't let them touch the pipeline.

**AI may change what CI checks. Never how.** For the ideas behind it, read
[Agents in CI: fix the build, not the pipeline](/guides/agents-in-ci/).

`referee` is a small standalone binary for projects that do **not** use
Itervox. It needs only `git`, works with any agent harness (Claude Code, Codex,
Aider, a shell script) and any CI, and enforces one rule:

> An agent may change **what** CI checks, never **how** CI checks.

A test, a fix, a new lint finding: what CI checks, fine. A workflow file, the
test runner's config, a coverage threshold, a `t.Skip`: how CI checks, so a
human looks first. Three properties make that hold:

- **The referee lives outside the branch.** The binary comes from the Action's
  pinned ref, not from the pull request.
- **The policy is read from the base branch** (`git show <base>:.referee.yml`),
  never from the working tree or the head. A pull request that edits the
  policy is judged by the old one, and the policy file itself is always in the
  human lane.
- **The writer is never the judge.** Checks can run through `referee run`,
  which signs what it saw with a key the agent cannot read.

## Install

```bash
brew install vnovick/tap/referee                           # Homebrew (macOS / Linux): only the referee
referee --version
```

Every Itervox release includes it: `itervox referee lanes --base origin/main`
runs the same code as the standalone `referee` binary, so with
`brew install vnovick/tap/itervox` you already have it. Without Homebrew:

```bash
go install github.com/vnovick/itervox/cmd/referee@latest   # or pin a version
# from a checkout of this repository:
make referee                                              # writes bin/referee
```

In GitHub Actions, use [the Action](#the-github-action), which builds it.

## The commands

### `referee lanes`

```bash
referee lanes --base origin/main [--head HEAD] [--policy .referee.yml] [--json]
```

Lists the files that differ between the merge base of `--base` and `--head`,
and `--head` (`git diff --name-only -z --no-renames`: a moved file counts as its
old path and its new one), and puts each in a lane:

| Lane | Meaning | Exit |
|---|---|---|
| `auto` | nothing in the policy matched | `0` |
| `second_opinion` | a reviewer other than the writer must approve | `10` |
| `human` | a human must approve this pipeline change | `20` |

The highest lane any file reaches is the result. Committed changes only:
uncommitted files in the working tree are not part of the diff.

The policy is `.referee.yml` (or `--policy <path>`), **read from the base
ref**, with two lists of gitignore-style globs:

```yaml
# .referee.yml on your default branch
human:
  - ".github/**"
  - "Makefile"
  - "jest.config.*"
  - "deploy/**"
second_opinion:
  - "src/auth/**"
  - "migrations/**"
```

- `*` and `?` match within one path segment; a `**` segment spans any number
  of directories; a pattern without a `/` matches that name at any depth;
  a leading `/` or any inner `/` anchors it at the repository root; a pattern
  that matches a directory matches everything under it; `!pattern` excludes
  what an earlier pattern of the same lane matched.
- A missing key takes its default; a list replaces the default; `[]` turns the
  lane off. Unknown keys and malformed patterns are errors (exit `2`), so a
  typo cannot fall back to the defaults silently. JSON works too.
- No policy file on the base ref: the default human lane, which is
  `.github/**`, `.gitlab-ci.yml`, `.circleci/**`, `.itervox/**` (but not
  `.itervox/handoff/**`), `WORKFLOW.md`, `CODEOWNERS`, `jest.config.*`,
  `vitest.config.*`, `pytest.ini`, `.coveragerc`, `codecov.yml`,
  `.golangci.yml` and `Makefile`. Build manifests (`package.json`,
  `pyproject.toml`, `go.mod`) are deliberately not in it: their tool sections
  cannot be told apart from their dependency lists by path.
- The policy file is always added to the human lane, last, so no `!` pattern
  can exclude it.
- `tools:` lists the deploy tools [`envcheck`](#referee-envcheck) inspects and
  [`diff`](#referee-diff) runs;
  `lanes` reads only its shape (an unknown key in it is still an error).

`--json` prints a stable shape (`version` 1):

```json
{
  "version": 1,
  "lane": "human",
  "exit_code": 20,
  "base": "origin/main",
  "base_commit": "…",
  "merge_base": "…",
  "head": "HEAD",
  "head_commit": "…",
  "policy": ".referee.yml@1a2b3c4d5e6f",
  "human": [".github/workflows/ci.yml"],
  "second_opinion": [],
  "auto": ["src/app.ts"]
}
```

With `GITHUB_STEP_SUMMARY` set (any GitHub Actions step), `lanes` also appends
a Markdown summary of the lanes and their files to the job summary.

### `referee audit`

```bash
referee audit --base origin/main [--head HEAD] [--json]
```

Reads the same diff and reports changes that weaken checks. Each rule is
small, looks only at **added** lines of the files where the construct means
what the rule says, and skips comment lines:

| Rule | Flags |
|---|---|
| `test_deleted` | a test file (`*_test.go`, `*.test.ts`, `*.spec.js`, `test_*.py`, `*_spec.rb`, `*Test.java`, `__tests__/…`) deleted or renamed |
| `go_skip` | `t.Skip(`, `t.SkipNow(`, `t.Skipf(` added in a `_test.go` file |
| `js_skip` | `it.skip(`, `test.skip(`, `describe.skip(`, `xit(` added in a JS/TS file |
| `js_only` | `it.only(`, `test.only(`, `describe.only(` added |
| `py_skip` | `@pytest.mark.skip`, `@pytest.mark.skipif`, `@unittest.skip` added |
| `coverage_lowered` | a coverage threshold (`fail_under`, `--cov-fail-under`, `branches`, `lines`, `functions`, `statements`, codecov `target`) set lower in the same hunk of a common coverage config file |
| `ci_continue_on_error` | `continue-on-error: true` (or GitLab `allow_failure: true`) added in a workflow |
| `ci_or_true` | `\|\| true` added in a workflow |
| `git_no_verify` | `git commit --no-verify`, `git push --no-verify` or `git commit -n` added in a script, Makefile, `package.json`, hook config or workflow |

`git push -n` is not flagged: for `push`, `-n` is `--dry-run`. A threshold
removed outright is not flagged either; the human lane covers the common
coverage config files. Exit `20` with any finding, `0` with none, `2` on an
error. `GITHUB_STEP_SUMMARY` gets a summary here too.

### `referee envcheck`

```bash
referee envcheck --base origin/main [--head HEAD] [--policy .referee.yml] [--json]
```

A dependency bump can change how a deploy CLI behaves without touching any
CI file. Say the repository's deploy step runs a guard script first, which
decides from a few environment variables which deployment a deploy may
target. A lockfile change installs a new version of the CLI that also reads
a new deploy-target variable. The guard does not know that variable, so it
cannot refuse a deploy that uses it. `lanes` sees only a lockfile and
`audit` sees nothing. `envcheck` scans the installed tool and fails when it
mentions a deploy-target variable that the guard does not classify.

Tools are listed under `tools:` in the policy, **on the base ref**:

```yaml
# .referee.yml on your default branch
tools:
  convex:                       # a built-in adapter
    guard: scripts/lib/deploy-target.mjs
  mycli:                        # a generic adapter: no Go code
    guard: scripts/lib/deploy-target.mjs
    env_scan: node_modules/mycli/dist/**/*.js
    env_pattern: 'process\.env\.([A-Z_][A-Z0-9_]*)'
    deploy_vars: [MYCLI_*]
    probes:
      - mycli deploy --dry-run
      - mycli --help
```

| Key | | |
|---|---|---|
| `guard` | required | the repository file that classifies the tool's deploy-target variables |
| `install` | optional | where the tool is installed (built-in: `node_modules/<package>`; generic: the directory part of `env_scan`) |
| `deploy_vars` | generic: required | globs (`*`, `?`) over variable names that choose where, or as whom, the tool deploys. On a built-in it replaces the adapter's list. `[]` is refused |
| `env_scan` | generic only, required | a repository-relative glob of the installed files to scan; `**` spans directories |
| `env_pattern` | generic only | a regular expression whose first group is a variable name. Without it, every word that matches `deploy_vars` counts |
| `probes` | optional | safe commands [`diff`](#referee-diff) runs on the base and head installs. Each must start with the tool's command and runs without a shell, so quotes, `$`, `;`, `\|`, `&` and redirections are refused. |
| `command` | generic only | the tool's executable name, which probes start with (default: the tool's key) |

The built-in adapters are deliberately small:

| Adapter | Install root | Deploy-target variables | Probes | Detected by |
|---|---|---|---|---|
| `convex` | `node_modules/convex` | `CONVEX_*` | `convex --version`, `convex deploy --help` | a `convex` dependency in `package.json`, or `convex.json` |
| `vercel` | `node_modules/vercel` | `VERCEL_*` | `vercel --version`, `vercel deploy --help` | a `vercel` dependency in `package.json`, `vercel.json` or `.vercel/project.json` |

A built-in scans the `.js`, `.cjs` and `.mjs` files under its install root.
Any other name under `tools:` is a generic adapter. A tool the repository
looks like it uses but `tools:` leaves out is printed as a note and does not
change the exit code.

What each side comes from:

- **The policy** (`tools:`): the base ref, as for `lanes`. A pull request
  cannot add, drop or repoint a tool for its own check.
- **The installed tool**: the working tree under `--dir`, so run `envcheck`
  after installing the head's dependencies (`npm ci`). That install is what
  the deploy will run. An install root that is missing, or has no file to
  scan, is an error (exit `2`), never a pass.
- **The guard**: git, at the base ref **and** at the head. A variable is
  classified only when both versions mention it. A pull request that drops a
  classification from its guard fails. So does one that classifies a new
  variable in the same change that starts reading it: land the guard change
  on the base branch first, where it is reviewed on its own. A guard missing
  on either side is an error.

"Classified" means the guard mentions the variable's name as a whole word
(`CONVEX_DEPLOY` is not mentioned by `CONVEX_DEPLOY_KEY`), in code, in a list
or in a comment. envcheck does not judge what the guard does with it.

**Limits.** A scan finds the variable names a tool's files mention, not
every way it can read one. It does not see a name built at run time
(`"CONVEX_" + x`), a variable read by a native binary or by a dependency
outside the install root, or a target chosen in a config file instead of a
variable. Symlinks below the install root are not followed (a symlinked
root, as pnpm installs, is). Install scripts run by
your package manager can change the installed files, so install with
`--ignore-scripts` before `envcheck` if you can. Treat `envcheck` as a
tripwire for the common case, not as proof.

Exit `0` when every deploy-target variable is classified (or there is no
`tools:` on the base ref, with a message saying so), `20` with an
unclassified one, `2` on an error. The exit for a finding is `20`, not `10`:
the fix is a change to the deploy guard, which a human owns. Each finding
names the tool, the variable and the `file:line` where the install first
mentions it:

```text
envcheck: 1 unclassified deploy-target variable(s) (policy: .referee.yml@1a2b3c4d5e6f)
  node_modules/convex/dist/cli.bundle.cjs:3  [convex] convex mentions CONVEX_TARGET_URL, a deploy-target variable the guard on the base ref does not classify
      add CONVEX_TARGET_URL to scripts/lib/deploy-target.mjs (on the base branch first)
  convex: 3 deploy-target variable(s) in node_modules/convex, guard scripts/lib/deploy-target.mjs
```

`--json` prints `version` 1 with `tools` (each with its `variables` and
parsed `probes`), `findings` (`tool`, `variable`, `path`, `line`, `guard`,
`message`) and `notes`. `GITHUB_STEP_SUMMARY` gets a summary here too.

### `referee diff`

```bash
referee diff --base origin/main --base-dir ../base [--head HEAD] [--policy .referee.yml] [--timeout 30s] [--json]
```

`envcheck` reads a tool's files; `diff` runs it. A dependency bump can make a
deploy CLI ask a new question, take a new flag, or say something different in
a dry run, again without touching any CI file. `diff` runs each configured
tool's `probes` against two installs, the base's and the head's, and reports
what changed: the exit code, the output, and new confirmation prompts.

It needs two installs of the dependencies:

- **The head install** is the working tree under `--dir`: install the head's
  dependencies first, as for `envcheck`.
- **The base install** is `--base-dir`: a second checkout of the **merge
  base** of `--base` and `--head` (or of the base commit itself) with *its*
  dependencies installed. `diff` checks that the directory is a git checkout
  at one of those two commits and is not the head's own directory; anything
  else is an error, so a mistake cannot compare the head with itself and pass.

A GitHub Actions job:

```yaml
jobs:
  tool-diff:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    # No deploy credentials in this job: the probes run the tools' code.
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - name: Install the head
        run: npm ci --ignore-scripts
      - name: Install the merge base next to it
        env:
          BASE_REF: ${{ github.base_ref }}
        run: |
          git worktree add --detach "$RUNNER_TEMP/base" "$(git merge-base "origin/$BASE_REF" HEAD)"
          (cd "$RUNNER_TEMP/base" && npm ci --ignore-scripts)
      # Pin to a commit SHA in real use.
      - uses: vnovick/itervox/referee@main
        with:
          mode: diff
          base-dir: ${{ runner.temp }}/base
          fail-on: second_opinion # fail the step on a behaviour change
```

Any CI works the same way: `git worktree add --detach <dir> <merge base>`,
install there, then `referee diff --base-dir <dir>`. Without `tools:` on the
base ref there is nothing to compare: `diff` exits `0` with a message and
needs no `--base-dir`.

**Where a probe's command comes from.** A probe starts with the tool's
command. For a tool installed under `node_modules/` it is
`node_modules/.bin/<command>` in each checkout; for any other install root,
`<install>/bin/<command>`, then `<install>/<command>`. It must be an
executable file whose target stays inside that checkout. It is never looked
up on `PATH`, where both sides would find the same program. A command
missing from either install is an error (exit `2`) before anything runs.

**How a probe runs.** Each probe runs twice, base first, with:

- **No shell.** The probe's argv as parsed from the policy, in its own
  checkout.
- **A scrubbed environment.** Only `PATH` comes from the runner (with the
  command's directory first). `HOME`, the `XDG_*` directories and `TMPDIR`
  point into a fresh empty directory, so no saved login or config of the
  runner's user is visible. `LANG` and `LC_ALL` are `C`, `TERM` is `dumb`,
  `NO_COLOR` is `1`. Nothing else is passed: no token, no cloud key, no
  `CI`, and no variable the tool's `deploy_vars` match, even from that list.
- **No input, but an open stdin.** Stdin is a pipe that `diff` holds open
  and never writes to, closed only after the probe has exited or been
  killed. A prompt is never answered and never reads end of input either,
  so a tool that asks a question does what it would do in front of a
  person: it waits.
- **Waiting for input is detected.** A probe that is still running and has
  printed nothing for **3 seconds** (the idle window; any output, even past
  the 64 KiB cap, restarts it) is taken to be waiting for input. Its whole
  process group is killed, the run is recorded with `waiting_for_input`,
  and its last non-empty output line is reported as the prompt it was
  waiting on (with or without a trailing newline). A tool that is silent for
  3 seconds for another reason (a slow start, a network call) looks the same;
  that is only a change when the other side did not wait.
- **A timeout** (`--timeout`, default 30 s), after which its whole process
  group is killed, children included. It bounds a probe that keeps printing.
  A process the tool leaves running after it exits is killed too.
- **An output cap.** stdout and stderr are read as one stream, and the first
  64 KiB are compared.

**What counts as a change.** Before comparing, the output is normalised:
ANSI colour is removed, a line redrawn with `\r` keeps what was left on
screen, the checkout path becomes `<checkout>` and the fresh home
`<home>`, and versions (`1.2.3`), timestamps, durations (`12ms`, `1.5s`),
UUIDs, long hex ids and temp paths become placeholders. A probe changed when
its exit code changed, when it timed out or waited for input on one side
only, when its normalised output differs, or when the head prints a new
**prompt**. A prompt is found two ways:

- **A head run waiting for input** where the base run did not wait: its last
  line is the prompt, whatever its wording (`Deploy to production?`,
  `Target:`, or `(waiting for input; nothing was printed)` when it printed
  nothing).
- **A prompt-like line** new on the head, even when the tool did not wait (it
  read a default, or printed the question to a log): a line with `[y/N]`,
  `(yes/no)` and the like, an inquirer-style `? …` question, "Are you sure",
  "Do you want to continue", "Press Enter". A head run that timed out with a
  question as the last thing it printed (a line ending in `?` or `:`) is
  reported as a prompt too.

Both sides waiting on the same question is not a change.

```text
diff: 1 of 3 probe(s) changed behaviour (policy: .referee.yml@1a2b3c4d5e6f, base install: ../base @ 9f8e7d6c5b4a)
  [mycli] mycli --version: unchanged (exit 0)
  [mycli] mycli deploy --help: changed (exit_code, waiting_for_input, output, prompt)
      base exit 0, head waiting for input
      new prompt: Deploy to production? [y/N]
      + Deploy to production? [y/N]
  [mycli] mycli env ls: unchanged (exit 0)
```

Exit `0` when no probe changed (or there is no `tools:`), `10` when one did,
and `2` on an error: a missing install on either side, a `--base-dir` that is
not a checkout of the base, or a probe that cannot start. The exit for a
change is `10`, the second-opinion code: a different help text is not
necessarily wrong, but a person should read it before the change deploys
anything.

`--json` prints `version` 1 with `base_commit`, `merge_base`,
`base_dir_commit`, `env` (the variable names a probe gets) and, per tool,
each probe's `base` and `head` runs (`executable`, `exit_code` (`-1` when
killed), `timed_out`, `waiting_for_input`, `prompt` (the last line of a run
waiting for input, else empty), `left_running`, `duration_ms`,
`output_bytes`, `output_truncated`) and its
`changes`, `added` and `removed` lines (the first 20 of each, with
`added_count` and `removed_count`) and new `prompts`. Lines are normalised
and redacted. `GITHUB_STEP_SUMMARY` gets a summary here too.

**Limits.** `diff` is not a sandbox:

- **No network isolation.** A probe can reach the network, and a tool that
  phones home or fetches something does so from your runner. Run `diff` in a
  job that holds **no deploy credentials** (no deploy key, no cloud token, no
  write-scoped `GITHUB_TOKEN`), as in the job above. The scrubbed environment
  keeps credentials out of the probe's variables, not out of files the job
  leaves readable.
- **Probes are only as safe as you write them.** They run the installed
  code of both versions. Use read-only commands: `--version`, `--help`,
  `deploy --help`, a `--dry-run` you trust. A probe may write files in its
  checkout.
- **What it sees is what the probes show.** A change behind a flag no probe
  passes, or one that only happens with real credentials, is not seen.
- **Normalising can hide a change** that only differs in a version-like or
  time-like token. A prompt worded unlike the patterns above is seen only
  when the tool waits for its answer (or through the output diff).
- Linux and macOS only.

### `referee pin`

```bash
referee pin --print [--file .referee.yml]
referee pin --policy-sha256 <hex> [--file .referee.yml]
```

Fails (exit `20`) when the file's sha256 is not the pinned one, and prints the
actual hash. Put the hash in the workflow file, which is itself human lane:
then the policy cannot change without a reviewed workflow change, even on a
repository where the base branch is not protected. Works for any file
(`WORKFLOW.md`, `CODEOWNERS`).

### `referee run`, `keygen` and `verify`

```bash
referee keygen --out "$RUNNER_TEMP/keys"          # attest.key (0600) + attest.pub
referee run --name test --key "$RUNNER_TEMP/keys/attest.key" --out checks.jsonl -- 'go test ./... | tee test.log'
referee run --name lint --key "$RUNNER_TEMP/keys/attest.key" --out checks.jsonl -- golangci-lint run
referee verify checks.jsonl --pubkey attest.pub --tree .
```

`run` runs one check and appends two signed records (ed25519): the check (its
real exit code, duration, the SHA-256 of its output and a redacted tail, the
git tree hash of the working tree it ran on, tracked plus untracked
non-ignored files, and `HEAD`) and a seal (the tree after it). One argument
after `--` is a shell command line, run by bash with `pipefail`, so a failing
command piped into `tee` or `tail` still fails; more arguments run directly
with no shell. It exits with the check's own exit code (`1` when the check was
killed, timed out or did not start) and `2` when it cannot sign or write the
record. It refuses a key inside the working tree: whatever the check runs
could read it.

`verify` checks every signature and that each check ran on the final tree;
`--tree DIR` also requires that tree to be `DIR`'s tree now, so "the tests
passed" is about this code, not some earlier version of it. Exit `0` when every
record verifies, `1` when one does not, `2` on an error.

See [Signed checks](/guides/signed-checks/) for what a record contains.

Keep the private key where the agent cannot read it (a CI secret available only
to the job that runs the checks, not to the job the agent runs in), and give
reviewers the public key.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | auto lane, no audit or envcheck findings, no diff behaviour change, pin matches, check passed, records verify |
| `1` | `run`: the check failed; `verify`: a record did not verify |
| `10` | `lanes`: second_opinion lane; `diff`: a tool's behaviour changed |
| `20` | `lanes`: human lane; `audit`, `envcheck`: findings; `pin`: mismatch |
| `2` | usage, git or I/O error (bad ref, malformed policy, missing file) |

referee fails closed: an error is never `0`. A base ref that is not in the
checkout is an error, not an empty diff; fetch it (`fetch-depth: 0`).

## The GitHub Action

`vnovick/itervox/referee` is a composite Action: it installs Go with
`actions/setup-go`, builds `referee` from the Action's own ref with
`go install ./cmd/referee`, and runs one mode.

| Input | Default | |
|---|---|---|
| `mode` | (required) | `lanes`, `audit`, `envcheck`, `diff`, `pin` or `verify` |
| `base` | `origin/<base branch>` | the ref the pull request merges into |
| `head` | `HEAD` | the ref under review |
| `policy` | `.referee.yml` | lanes, envcheck, diff: the policy path on the base ref; pin: the file to hash |
| `policy-sha256` | | pin: the pinned hash |
| `fail-on` | `human` | lanes: `human`, `second_opinion` or `never`; audit, envcheck: `never` reports without failing; diff: `second_opinion` fails on a behaviour change (otherwise a warning) |
| `base-dir` | | diff: the checkout of the merge base with its dependencies installed |
| `records`, `pubkey`, `tree` | | verify |

Outputs: `lane` (lanes) and `exit-code`. An error fails the step whatever
`fail-on` says.

Pin the Action to a commit SHA. Do not use it as `uses: ./referee` from the
repository under review: the pull request could change the referee.

### Example: human-lane pull requests need a label

```yaml
name: referee

on:
  pull_request:
    types: [opened, synchronize, reopened, labeled, unlabeled]

permissions:
  contents: read

jobs:
  lanes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0 # the merge base and the base branch's policy
          persist-credentials: false
      # Pin to a commit SHA in real use.
      - id: lanes
        uses: vnovick/itervox/referee@main
        with:
          mode: lanes
          fail-on: never # decided below, with the label
      - id: audit
        uses: vnovick/itervox/referee@main
        with:
          mode: audit
          fail-on: never # decided below, with the label
      - name: Pipeline changes need the pipeline-approved label
        if: >-
          (steps.lanes.outputs.lane == 'human' || steps.audit.outputs.exit-code == '20')
          && !contains(github.event.pull_request.labels.*.name, 'pipeline-approved')
        run: |
          echo "::error::This pull request changes how CI checks (human lane, or checks weakened: see the job summary). A maintainer must review it and add the pipeline-approved label."
          exit 1
```

Make the job a required check in branch protection. The same file is
`referee/examples/referee-pr.yml` in the repository.

**The trade-off.** The workflow checks the label by name, not who added it.
Anyone with triage access can add labels, and so can any token with pull
request write access, so the agent's token must never have that permission
(otherwise the agent can approve itself). The label also stays on when more
commits are pushed after it was added. If that matters, remove the label on
every `synchronize` in a separate workflow with `pull-requests: write`, or
check the label event's actor and permission through the API, or use
CODEOWNERS with required reviews on the same paths instead of a label. referee
itself does not authenticate labels: it only decides the lane.

## With any harness

The enforcement is the CI job on the base branch's policy. Anything run next
to the agent is early feedback the agent can read; it is not a control,
because the agent can edit or skip it.

**A plain shell CI step** (GitLab, Jenkins, Buildkite, anything with git):

```bash
git fetch --no-tags origin main
referee lanes --base origin/main; lane=$?
referee audit --base origin/main; audit=$?
case "$lane" in 0|10) ;; 20) echo "pipeline change: needs a human" ;; *) exit 2 ;; esac
[ "$lane" -ne 20 ] && [ "$audit" -eq 0 ] || exit 1
```

**Claude Code.** A `Stop` hook in `.claude/settings.json` shows Claude what
the referee will say before it finishes. A hook command that exits `2` blocks
and its stderr goes back to Claude:

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "referee audit --base origin/main >&2 || exit 2" }
        ]
      }
    ]
  }
}
```

**Codex, Aider and others.** Run the agent in one job (or step) and referee in
a later one that the agent's job cannot change: `codex exec …` or
`aider --message … --yes` then `referee lanes` and `referee audit` on the
pushed branch. Aider's `--test-cmd` can also run `referee audit --base
origin/main` so its own test loop sees the findings.

**Git hooks.** `referee lanes --base origin/main` in a `pre-push` hook warns
early. An agent can push with `--no-verify`, which `referee audit` reports
when it lands in a script, and which CI does not care about either way.

## Using Itervox?

Itervox has the same rule built in: [guardrails lanes](/guides/guardrails/)
hold a push that changes human-lane files for an approval, and signed checks
(`agent.profiles.<name>.verify`, `itervox attest verify`) use the same record
format as `referee run`. See [Lanes](/guides/lanes/),
[Signed checks](/guides/signed-checks/) and the
[pipeline-guard demo](/guides/pipeline-guard-demo/), which runs
`referee lanes` and `referee verify` with `--referee`.
