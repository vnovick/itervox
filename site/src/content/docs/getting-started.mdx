## Install

Itervox is a single Go binary. Install it with Homebrew:

```bash
brew tap vnovick/tap && brew install itervox
```

Or download the latest release from [GitHub Releases](https://github.com/vnovick/itervox/releases).

On Windows, download `itervox_windows_amd64.zip` (or `_arm64`) from the release, put `itervox.exe` on your PATH and install Git for Windows: see [Running on Windows](/guides/windows/).

On a Mac, the [menu bar app](/guides/desktop-app/#install) is the other option: `brew install --cask vnovick/tap/itervox-app`. It carries its own `itervox` daemon, so install one or the other, not both.

The [desktop app](/guides/desktop-app/) also runs on Linux and Windows, from the same release page:

| Platform | Download | Guide |
|---|---|---|
| macOS (Apple silicon and Intel) | `Itervox_<version>_universal.dmg`, or `brew install --cask vnovick/tap/itervox-app` | [Install](/guides/desktop-app/#install) |
| Linux x86_64 / arm64 | `Itervox_<version>_amd64.AppImage` / `_aarch64.AppImage`, or `Itervox_<version>_amd64.deb` / `_arm64.deb` | [Install on Linux](/guides/desktop-app/#install-on-linux) |
| Windows x86_64 | `Itervox_<version>_x64_en-US.msi` or `Itervox_<version>_x64-setup.exe` | [Windows](/guides/desktop-app/#windows) — local projects need WSL or a remote daemon for now |


## Prerequisites

- **An AI agent CLI** — one of:
  - [Claude Code](https://docs.anthropic.com/en/docs/claude-code) (`claude`)
  - [Codex](https://github.com/openai/codex) (`codex`)
- **A project tracker** — Linear or GitHub Issues, or none: the [local tracker](/guides/local-issues/) keeps issues as Markdown files in your repository

## Try it first: `itervox demo`

```bash
itervox demo
```

Opens a throwaway board with fake issues and a scripted agent: no tracker account, API keys or agent CLI needed, and nothing is written outside a temporary directory. Within about a minute you see issues run, ask for input, fail and retry, go to review and finish. See [`itervox demo`](/cli/#itervox-demo--try-it-in-30-seconds).

## Quickstart: one command

In your project repository:

```bash
itervox quickstart
```

It takes you from a repository to a running board:

1. **Detects** the tracker and the agent CLI. `LINEAR_API_KEY` set → Linear; otherwise an `origin` remote on github.com → GitHub Issues; otherwise the [local tracker](/guides/local-issues/). The agent is `claude` if it is on your `PATH`, otherwise `codex`. Override either with `--tracker github|linear|local` and `--runner claude|codex`.
2. **Writes `WORKFLOW.md`** (schema 2) and the `.itervox/agents/` profiles, the same files `itervox init` writes. An existing schema-2 workflow is used as it is; an older one is migrated with `itervox init --update` only after you confirm.
3. **Sets up the tracker token.** For GitHub without `GITHUB_TOKEN`, it offers your `gh` CLI's token (`gh auth token`) and saves it to the gitignored `.itervox/.env` if you agree. For Linear, put `LINEAR_API_KEY` in `.itervox/.env` first.
4. **Creates missing GitHub state labels** after asking (the same step as `itervox doctor --fix`).
5. **Runs `itervox doctor`** and stops with its report if anything is wrong.
6. **Starts the daemon in the background**, waits for `/api/v1/ready`, and prints the dashboard URL and the file that holds the API token. The daemon's output goes to `.itervox/logs/quickstart-daemon.log`; stop it with `itervox stop`.

Re-running is safe: nothing is overwritten without asking, and if the daemon is already running quickstart prints its URL instead of starting another. Pass `--yes` to accept every prompt (for scripts) or `--no-start` to stop after the checks.

The steps below do the same by hand.

## Manual setup

### 1. Initialize WORKFLOW.md

Navigate to your project repo and run:

```bash
itervox init --tracker linear --runner claude
```

This scans your repository, detects the tech stack, and generates a schema `2` `WORKFLOW.md` starter plus `.itervox/agents/implementer`, `.itervox/agents/reviewer`, and `.itervox/agents/input-responder` profile files.

For GitHub Issues:

```bash
itervox init --tracker github --runner claude
```

GitHub tracks states as **labels**, so create them before the first run (`itervox doctor --fix` does it for you), and authenticate the `gh` CLI. The [GitHub Issues guide](/guides/github-issues/) covers labels, `p0`–`p3` priority labels, blocker phrases, `#42` identifiers and `gh auth`.

### 2. Configure secrets

Create a `.itervox/.env` file (gitignored) with your API keys:

```bash
# For Linear
LINEAR_API_KEY=lin_api_xxxxx

# For GitHub (use a personal access token with repo scope)
GITHUB_TOKEN=ghp_xxxxx
```

Reference them in WORKFLOW.md as `$LINEAR_API_KEY` or `$GITHUB_TOKEN`.

#### Linear: choose what Itervox reads

A Linear tracker's scope is the **AND** of three optional filters. Leave them all out to read every project.

```yaml
tracker:
  kind: linear
  api_key: $LINEAR_API_KEY
  project_slug: ENG          # only this project (omit: every project)
  assignee: me               # only issues assigned to this user: me, a user id or an email (omit: anyone)
  labels: ["agent"]          # only issues carrying ANY of these labels (omit: no label filter)
```

| Set | Itervox reads |
|---|---|
| nothing | every issue the key can read, in every project |
| `project_slug` | that project's issues (as before) |
| `assignee` | that user's issues across every project and team the key can read (`team: ENG` narrows to one team) |
| `project_slug` + `assignee` | that user's issues inside the project |
| `labels` with any of the above | only the issues among them carrying at least one of the labels |

With `assignee: me` a dedicated "Itervox" Linear user can own the agent lane: assign a ticket to it to hand it to the agents, reassign it to take it back. Itervox never changes an issue's assignee or labels itself, so a run never moves its own issue out of scope. Change the scope at runtime in the dashboard's **Settings → Tracker Scope**. `itervox doctor` checks that the assignee resolves and its issues are readable. See [Linear setup → Scope](/guides/linear-setup/#scope-project-assignee-labels).

Need OR, exclusions or more fields? Replace those keys with `tracker.filter`, a list of groups: every condition in a group must match, any group matching reads the issue (Linear and GitHub):

```yaml
tracker:
  filter:
    - projects: [ENG]
      labels_any: [agent, ai]
      labels_none: [blocked]
    - assignee: me
      labels_all: [urgent]
```

See [Tracker filter](/configuration/#tracker-filter); Settings → Tracker Scope builds it with a live match count, and `itervox doctor` prints how many issues it matches.

Commit `.itervox/agents/**`; those files define your project agent profiles. Do not commit `.itervox/.env`, `.itervox/HEARTBEAT.md`, logs, or runtime queue files.

### 3. Run

```bash
itervox
```

Itervox starts polling your tracker, spawning agents for active issues, streaming logs to the terminal, and writing `.itervox/HEARTBEAT.md` with current daemon state. By default it loads `WORKFLOW.md` from the current directory; pass `-workflow <path>` only if it lives elsewhere.

Open the dashboard to see the Kanban board. If you omitted `server.port` from `WORKFLOW.md`, it defaults to `http://localhost:8090` — but `itervox init` scaffolds `server.port: 0` (OS-assigned), so don't assume 8090 blindly. Find the actual URL in `.itervox/dashboard_url` or the `dashboard URL:` line of `itervox doctor` — both give the **token-free** URL (no bearer token is stored there). The dashboard also needs the bearer token, which comes from one of: the tokenised URL printed once on the startup terminal's stderr (only when stderr is a terminal), `<logs-dir>/api-token` for an auto-generated token (mode 0600; `<logs-dir>` defaults to `~/.itervox/logs/<kind>/<slug>-<project>/`), or the value you pinned as `ITERVOX_API_TOKEN` in `.itervox/.env`. See [Remote access → The API token](/guides/remote-access/#the-api-token).

### 4. (Optional) Verbose mode

```bash
itervox -verbose
```

Enables DEBUG-level logging including agent output.

## Workspace setup

Each issue runs in its own git worktree, which holds only what git tracks.
Two `workspace` settings get it ready for the agent:

- **Files the project needs but does not commit.** List them in
  `workspace.copy_files` (paths or globs from the repository root). They are
  copied from your checkout into each new worktree before
  `hooks.after_create` runs, and refreshed on later runs unless the
  worktree's copy is newer. Only gitignored files are copied: a tracked or
  unignored match is skipped with a warning, so a copied file can never be
  committed from the worktree. `itervox init` suggests `.env` and
  `.env.local` when they exist and are gitignored. Values from a copied
  dotenv file are masked in Itervox's logs, but **the agent can read every
  copied file** — copy only what you would hand it.
- **A port per workspace.** Each issue's workspace gets its own TCP port
  from `workspace.port_range` (default `41000-41999`) as `ITERVOX_PORT`, in
  the agent's environment and every hook's, so several agents can run dev
  servers at once. Prompts can use `{{ run.port }}`, and the issue's **Now**
  panel shows it. The port stays with the issue while its worktree exists,
  survives a daemon restart, and is released when the worktree is cleared.

```yaml
workspace:
  worktree: true
  copy_files: [".env", ".env.local"]
  port_range: "41000-41999"
```

```bash
# hooks.after_create — .env and ITERVOX_PORT are both there already
pnpm install --frozen-lockfile
pnpm run db:migrate
# and in the prompt or a hook: pnpm dev --port "$ITERVOX_PORT"
```

With SSH workers nothing is copied over: the agent runs in the same
workspace path on the worker host, which must be shared with this machine.
See [Workspace setup](/configuration/#workspace-setup) for the full rules.

## What happens next

1. Itervox polls your tracker for issues in active states (default: "Todo", "In Progress")
2. For each issue, it creates an isolated workspace (clone or worktree)
3. An AI agent is spawned with your `WORKFLOW.md` prompt template plus the selected profile's `SOUL.md` and `INSTRUCTIONS.md`
4. The agent works on the issue, creates a branch, and submits a PR
5. If the agent needs a human decision, Itervox pauses the issue in `input_required` and lets you reply from the dashboard or tracker
6. Otherwise Itervox transitions the issue state on success

All of this is visible in real time via the web dashboard, or from a terminal with `itervox watch` and `itervox logs -f <issue>`.

## The spec behind Itervox

Itervox is the reference implementation of the [**Orchestrated Coding** spec](https://github.com/vnovick/orchestrated-coding) — a vendor-neutral system spec for running fleets of coding agents reliably (one orchestrator owning dispatch, isolated worktrees, durable handoffs, deterministic merge gates). Itervox **conforms at L3**, the spec's highest level, with evidence-linked verification. See [The Orchestrated Coding Spec](/guides/orchestrated-coding/) for the full mapping and the conformance story.
