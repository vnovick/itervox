## Usage

```
itervox [flags]
itervox <command> [flags]
```

When no command is given, `itervox` starts the daemon (run mode).


---

## `itervox` — Start the daemon

Reads `WORKFLOW.md`, connects to your issue tracker, and begins orchestrating agent workers.

### Flags

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `-workflow` | string | `WORKFLOW.md` | Path to your `WORKFLOW.md` configuration file |
| `-logs-dir` | string | `~/.itervox/logs/<kind>/<slug>-<project>` (or `~/.itervox/logs/workflow/<project>` when no `project_slug` is set) | Directory for rotating log files |
| `-verbose` | bool | `false` | Enable DEBUG-level logging (includes agent subprocess output) |
| `-shutdown-grace` | duration | `30s` | Grace period for active workers on `SIGINT`/`SIGTERM` before force exit |
| `-no-print-token` | bool | `false` | Never print the tokenised dashboard URL on stderr (by default it is printed only when stderr is a terminal). An auto-generated token is still written to `<logs-dir>/api-token` (mode 0600) |

> To try Itervox without a tracker account, API keys or an agent CLI, run
> [`itervox demo`](#itervox-demo--try-it-in-30-seconds).

### Examples

```bash
# Start with defaults (WORKFLOW.md in the current directory)
itervox

# Use a custom WORKFLOW.md location
itervox -workflow path/to/WORKFLOW.md

# Enable verbose logging and a longer shutdown grace period
itervox -verbose -shutdown-grace 60s

# Write logs to a specific directory
itervox -logs-dir /var/log/itervox
```

## `itervox demo` — Try it in 30 seconds

```bash
itervox demo [--dir <scratch>] [--no-open]
```

Runs a throwaway daemon against ten fake `DEMO-n` issues with a scripted agent, and opens the dashboard. It needs no tracker account, no API keys and no `claude` or `codex` on your `PATH`.

Within about a minute the board shows issues moving through **In Progress** (with streamed agent activity and a fake pull request, linked in a comment on the issue), **input required** (DEMO-2 and DEMO-7 ask a question that the demo answers itself after a few seconds), **a failure and a retry** (DEMO-4 and DEMO-9 fail their first run), **In Review**, and **Done** (the demo stands in for the reviewer after a few seconds). The header shows a **Demo mode** badge.

| Flag | Default | Description |
|---|---|---|
| `--dir` | a new temporary directory | Scratch directory for the demo. A directory that already holds a non-demo `WORKFLOW.md` is refused, so a real project's workflow is never overwritten; a previous demo's directory is reused. |
| `--no-open` | `false` | Do not open the dashboard in a browser; the URL is in `<dir>/.itervox/dashboard_url`. |

Everything the daemon writes stays in the scratch directory: `WORKFLOW.md`, `logs/`, `workspaces/` and `.itervox/`. Tools it runs (such as `gh` and `git`) get `XDG_*` and `GH_CONFIG_DIR` pointed at `.xdg/` there, so they write nothing in your home directory and do not use your own `gh` login. The dashboard listens on an OS-assigned port on `127.0.0.1` without a token. `ITERVOX_SERVER_PORT`, `ITERVOX_SERVER_HOST`, `PORT`, `ITERVOX_API_TOKEN` and `ITERVOX_DRY_RUN` are ignored for the demo. Stop it with `q` in the terminal UI, `Ctrl-C`, or `itervox stop -workflow <dir>/WORKFLOW.md`, then delete the directory.

## `itervox quickstart` — From a repository to a running board

```bash
itervox quickstart [--tracker github|linear] [--runner claude|codex] [--dir .] [--workflow path] [--yes] [--no-start]
```

| Flag | Default | Description |
|---|---|---|
| `--tracker` | detected | Tracker for a **new** workflow. Detected as Linear when `LINEAR_API_KEY` is set, else GitHub when `origin` is on github.com. |
| `--runner` | detected | Agent CLI for a new workflow: `claude` if on `PATH`, else `codex`. |
| `--dir` | `.` | Repository directory (the workflow's directory when only `--workflow` is given). |
| `--workflow` | `<dir>/WORKFLOW.md` | Workflow path. The `.itervox/.env` next to it is loaded even when you run quickstart from another directory. |
| `--yes`, `-y` | `false` | Answer yes to every confirmation (migration, saving the `gh` token, creating labels, adding the issue template). |
| `--no-start` | `false` | Stop after the checks; do not start the daemon. |
| `--ready-timeout` | `90s` | How long to wait for the daemon to report ready. |

Steps, in order:

1. With no workflow, write a schema-2 `WORKFLOW.md` and the `.itervox/agents/` profiles exactly as `itervox init` does. It also offers the [agent-ready issue template](/guides/github-issues/#agent-ready-issue-template). With a schema-2 workflow, use it unchanged; with an older one, ask before migrating it with `itervox init --update` (which keeps `WORKFLOW.md.bak`).
2. If a daemon is already running for this workflow, print its dashboard URL and stop. Otherwise remove a `HEARTBEAT.md` and `dashboard_url` left behind by a daemon that died (the next daemon rewrites both).
3. Make sure the tracker credential is set: for GitHub, offer `gh auth token` and save it as `GITHUB_TOKEN` in `.itervox/.env` (0600, gitignored) after confirmation; a real value already in that file is never replaced. For Linear, `LINEAR_API_KEY` must be set.
4. Run `itervox doctor --fix`: missing GitHub state labels are created after confirmation. Any doctor error stops quickstart with the report.
5. Start the daemon in its own session (output in `.itervox/logs/quickstart-daemon.log`), wait until it publishes `.itervox/dashboard_url` and `GET /api/v1/ready` returns 200, then print the URL and where the API token is: `<logs-dir>/api-token` for a generated token, or your `ITERVOX_API_TOKEN`.

Exit code `0` when the board is running (or already was, or `--no-start` passed the checks); `1` when a step stopped it.

## `itervox init` — Generate WORKFLOW.md

Scans the repository and generates a `WORKFLOW.md` starter file pre-populated with detected project metadata.

### Flags

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--tracker` | string | _(required)_ | Issue tracker: `linear` or `github` |
| `--runner` | string | `claude` | Agent runner backend: `claude` or `codex` |
| `--output` | string | `WORKFLOW.md` | Output file path |
| `--workflow` | string | `WORKFLOW.md` | Workflow path to migrate when `--update` is set |
| `--dir` | string | `.` | Directory to scan for repo metadata |
| `--force` | bool | `false` | Overwrite output file if it already exists |
| `--update` | bool | `false` | Migrate an existing workflow to the latest schema without requiring `--tracker` |
| `--issue-template` | bool | `false` | Add the agent-ready issue template without asking: `.github/ISSUE_TEMPLATE/agent-task.md` for GitHub (never over an existing file), printed for Linear. Without it, init asks `[y/N]` when run in a terminal and skips the question otherwise (it never waits on a pipe). See [Agent-ready issue template](/guides/github-issues/#agent-ready-issue-template). |

### Auto-detection

`itervox init` inspects the target directory and fills in the generated `WORKFLOW.md` with discovered values:

- **Git remote** — reads `origin` remote URL to derive the GitHub owner/repo slug and SSH clone URL
- **Default branch** — detects `main` or `master` from the local git configuration
- **Tech stacks** — detects Go, Node.js, Rust, Python, Elixir, and Ruby by the presence of language-specific manifest files (`go.mod`, `package.json`, `Cargo.toml`, `pyproject.toml` / `requirements.txt`, `mix.exs`, `Gemfile`)
- **Package manager** — Node.js commands are generated with `pnpm`
- **CLAUDE.md** — if a `CLAUDE.md` file is present in the scanned directory, the generated prompt template references it automatically
- **Available models** — queries the selected runner CLI (e.g. `claude --list-models`) to discover available models and writes them to `agent.available_models` in the generated file. Falls back to a built-in default list if the CLI does not support model listing.

After writing `WORKFLOW.md`, `itervox init` also creates `.itervox/agents/<profile>/SOUL.md`, `.itervox/agents/<profile>/INSTRUCTIONS.md`, `.itervox/.env` (with a placeholder API key for the chosen tracker), and `.itervox/.gitignore` if they do not already exist. Commit `.itervox/agents/**`; keep `.itervox/.env`, `.itervox/HEARTBEAT.md`, logs, and runtime queue files ignored.

### Example output

```
itervox init: scanning .
  git remote : git@github.com:acme/backend.git
  branch     : main
  runner     : claude
  CLAUDE.md  : found — prompt will reference it
  stack      : Go (go test -race ./cmd/... ./internal/..., golangci-lint run)
itervox init: wrote WORKFLOW.md
itervox init: wrote .itervox/agents profiles
itervox init: wrote .itervox/.env
```

### Examples

```bash
# Generate WORKFLOW.md for a GitHub project using Claude
itervox init --tracker github

# Generate WORKFLOW.md for a Linear project using Codex
itervox init --tracker linear --runner codex

# Scan a subdirectory and write to a custom path
itervox init --tracker github --dir ./myrepo --output myrepo/WORKFLOW.md

# Overwrite an existing WORKFLOW.md
itervox init --tracker github --force

# Migrate an existing inline-profile workflow to schema 2 profile files
itervox init --update --workflow WORKFLOW.md
```

`itervox init --update` creates `WORKFLOW.md.bak`, extracts each legacy inline `agent.profiles.<name>.prompt` into `.itervox/agents/<name>/INSTRUCTIONS.md`, creates compact `SOUL.md` files, rewrites the profile to `soul_file` and `instructions_file`, and sets `itervox_schema_version: 2` as the first key of the front matter. It also patches broad root `.gitignore` rules so `.itervox/agents/**` remains committable. Comments, key order, quoting and indent width in `WORKFLOW.md` are preserved — only the migrated keys change, so the diff against `WORKFLOW.md.bak` is small enough to review line by line.

## `itervox doctor` — Check a workflow

```bash
itervox doctor [--workflow PATH] [--clear-startup-error] [--deploy] [--fix [--yes]] [--upgrade]
```

Validates `WORKFLOW.md` (schema 2, dispatch checks, profile commands, skill and subagent references, GitHub state labels) and the local daemon files. Exits `0` when clean, `1` on any warning or failed check, `2` when the check itself cannot run.

| Flag | Description |
|---|---|
| `--workflow` | Path to `WORKFLOW.md` (default `WORKFLOW.md`) |
| `--clear-startup-error` | Remove `.itervox/STARTUP_ERROR.md` after fixing its cause |
| `--fix` | Create missing GitHub state labels after a `[y/N]` prompt; `--yes` / `-y` skips it |
| `--deploy` | Also probe agent credentials, `gh auth`, git push auth (dry run), the tracker API and the running daemon's `/api/v1/ready` |
| `--upgrade` | Print only the v0.2.1 upgrade notes that apply to this workflow and environment, each with its fix and a link to the note. See below. |

### Upgrade check (`--upgrade`)

`itervox doctor --upgrade` reads the workflow's front matter (raw, so a config that no longer loads is still explained), the environment with `.itervox/.env` loaded, and the machine, and prints each applicable note as:

```text
[note 19] A set PORT environment variable now moves the dashboard
  why:  `PORT=3000` is set in this environment; the dashboard now binds that port instead of `server.port`
  fix:  if `PORT` belongs to another project, unset it for the daemon or set `ITERVOX_SERVER_PORT`
  see:  https://github.com/vnovick/itervox/blob/main/CHANGELOG.md#021--2026-09-28 (note 19)
```

With nothing to change it prints one `upgrade: all clear` line and exits `0`; with any note it exits `1`; when the workflow cannot be read it exits `2`. It runs on its own: combine it with `--deploy` or `--fix` and it exits `2`. Run it before and after upgrading from v0.2.0 or earlier.

| Note | Applies when |
|---|---|
| 5 — per-project workspace and log paths | `workspace.root` is unset and `~/.itervox/workspaces` still holds worktrees in the old shared layout, or this project's v0.2.0 log directory (`~/.itervox/logs/<kind>/<slug>`, or `~/.itervox/logs` with no slug) still holds runtime state |
| 6 — `server.port` defaults to 8090 | no port is set (`server.port`, `ITERVOX_SERVER_PORT`, `PORT`) and another process already holds 8090 (this project's own daemon does not count) |
| 9 — `dependencies.auto_analyze` deprecated | the key is set |
| 10 — headless token no longer printed | an `itervox.service` unit is installed and `ITERVOX_API_TOKEN` is pinned neither in the environment, `.itervox/.env`, nor `/etc/itervox/secrets.env` / `/run/itervox/env` |
| 11 — SSH host-key checking values validated | `agent.ssh_strict_host_checking` or a `ssh_strict_host_by_host` entry is not one of `yes`, `no`, `ask`, `accept-new`, `off` |
| 12 — `.WORKFLOW.md.lock` | the `.gitignore` next to `WORKFLOW.md` does not ignore it |
| 13, 14 — unauthenticated origin and host checks | `server.allow_unauthenticated: true` (or the old `_lan` key) with no `server.allowed_hosts` |
| 15 — `itervox stop` and old PID files | `.itervox/daemon.pid` was written by a pre-v0.2.1 daemon |
| 17, 22 — drain on SIGTERM, new systemd unit | the installed unit lacks `--shutdown-grace` or `KillMode=mixed` |
| 19 — `PORT` moves the dashboard | `PORT` is set (even empty) and `ITERVOX_SERVER_PORT` is not; an invalid value is reported as a startup failure |
| 20 — headless JSON stderr | `ITERVOX_LOG_FORMAT=json` |
| Breaking (#48) — token auth on loopback | this project ran a pre-v0.2.1 daemon (state in its v0.2.0 per-slug log directory, or an old PID file) on a loopback or default host, auth is not disabled, and no `ITERVOX_API_TOKEN` is pinned |
| Breaking — `allow_unauthenticated_lan` renamed | the old key is set |
| CORE-115 — backend contradicts command | `agent`, a profile, or a `rate_limited` rule's `switch_to_backend` asks for the other backend than the command runs (the rule's `switch_to_profile` command, else `agent.command`, which defaults to `claude`); such a rule now stops the config from loading |

Not reported: notes with nothing to change in a config (1–4, 7, 8, 16, 18, 21, 25–27; note 2 concerns Linear only and note 4 only setups with a project filter and automations, but neither needs a config change), deployment packaging (23, 24, 28–30), and keys that are new in v0.2.1, so no earlier config has them (`agent.backend_fallback`, `server.allowed_hosts` entry format). A malformed new key makes the config fail to load, which plain `itervox doctor` reports. Read every note in the [v0.2.1 CHANGELOG](https://github.com/vnovick/itervox/blob/main/CHANGELOG.md#021--2026-09-28).

## `itervox clear` — Remove workspace directories

Removes git worktree workspace directories that Itervox created under the workspace root configured in `WORKFLOW.md`.

### Flags

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `-workflow` | string | `WORKFLOW.md` | Path to `WORKFLOW.md` (used to locate `workspace.root`) |

### Arguments

```
itervox clear [identifier ...]
```

Pass one or more issue identifiers (e.g. `ENG-42`, `123`) to remove only those workspaces. Omit all identifiers to remove every workspace under the workspace root.

### Examples

```bash
# Remove all workspaces
itervox clear

# Remove workspaces for specific issues
itervox clear ENG-42 ENG-99

# Use a non-default WORKFLOW.md location
itervox clear -workflow path/to/WORKFLOW.md ENG-42
```

## Environment variables

### Tracker credentials

| Variable | Required for | Description |
|----------|-------------|-------------|
| `LINEAR_API_KEY` | Linear tracker | Personal API key from your Linear workspace settings |
| `GITHUB_TOKEN` | GitHub tracker | Personal access token (or fine-grained token) with `repo` scope |

### Runtime options

| Variable | Default | Description |
|----------|---------|-------------|
| `ITERVOX_DRY_RUN` | `""` | Set to `"1"` to enable dry-run mode. The orchestrator logs dispatch decisions but does **not** start agent workers. Useful for verifying configuration and dispatch logic without consuming API tokens. |
| `ITERVOX_API_TOKEN` | `""` | Enables bearer-token authentication on all `/api/v1/*` routes (except `/api/v1/health`). Requests must include `Authorization: Bearer <token>`. When unset, Itervox auto-generates an ephemeral token at startup on **every** bind — including loopback — unless `server.allow_unauthenticated: true` (renamed from `server.allow_unauthenticated_lan`, which still parses as a deprecated alias). The dashboard URL that carries the token is printed to stderr once, only when stderr is a terminal (see `ITERVOX_PRINT_TOKEN`); an auto-generated token is also written to `<logs-dir>/api-token` (mode 0600, rewritten on every start), which is where a headless run (systemd, containers) finds it. Pin a stable value in `.itervox/.env` for bookmarks that survive restarts. |
| `ITERVOX_PRINT_TOKEN` | `""` | `1`/`true` prints the tokenised dashboard URL on stderr even when stderr is not a terminal; `0`/`false` suppresses it even on a terminal. Unset: printed only on a terminal. `-no-print-token` always wins. |

### Auto-loading

Itervox loads environment variables automatically at startup from the first file found in this order:

1. `.itervox/.env` (recommended — already gitignored by `itervox init`)
2. `.env`

Existing process environment variables are **never overwritten** by these files. Both files are optional; if neither exists the process environment is used as-is.

## Heartbeat

When the daemon starts, it writes `.itervox/HEARTBEAT.md` beside the active `WORKFLOW.md`. The file is generated atomically and refreshed at a bounded interval after state changes. It contains the workflow path, schema version, dashboard URL, tracker/project, capacity, automation queue pressure, dependency audit summary, input-required count, retry count, and last notable error. It is runtime state and should stay ignored.

## Logging

**Location:** `~/.itervox/logs/<kind>/<slug>-<project>/itervox.log` (or `~/.itervox/logs/workflow/<project>/itervox.log` when no `project_slug` is set)

The path is derived from the `tracker.kind` and `tracker.project_slug` fields in `WORKFLOW.md`. You can override it with the `-logs-dir` flag.

**Rotation:**

| Setting | Value |
|---------|-------|
| Max file size | 10 MB |
| Max backup files | 5 |
| Compression | gzip |

**Levels:**

| Level | When active |
|-------|-------------|
| `INFO` | Default — startup events, worker lifecycle, errors |
| `DEBUG` | With `-verbose` — includes agent subprocess output and detailed trace events |

Logs are written simultaneously to stderr and the rotating file so you can tail both in real time.
